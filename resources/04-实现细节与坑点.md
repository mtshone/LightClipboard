# 04 · 实现细节与坑点

本文档记录**真机上踩过的坑**：现象 → 根因 → 解法 → 代码位置。
改剪切板、图片、拖拽、面板显隐相关代码前请先读一遍；末尾的「不可回退清单」请勿删除。

---

## 1. 剪切板被其他程序独占（CLIPBRD_E_CANT_OPEN）

**现象**：偶发读不到剪切板内容，日志出现 `读取剪切板失败: ... CLIPBRD_E_CANT_OPEN`，那条复制记录丢失。

**根因**：剪切板是全局共享资源。别的程序正在 `OpenClipboard`/写入时，本进程的 `Clipboard.GetText()` 会抛
`COMException`。

**解法**：整个"读取 + 解析"包在退避重试里：最多 3 次，间隔 50ms / 100ms / 150ms。

**位置**：`Services/ClipboardDataParser.cs` → `TryRead` / `ReadCore`

**回归保护**：自检分组「剪切板读写（文本 / Emoji / 图片）」。

---

## 2. 自身写入剪切板导致的死循环

**现象**：点击卡片"复制到剪切板"后，该条记录又被当成新内容重新入库（时间戳反复刷新，甚至列表跳动）。

**根因**：本程序写剪切板同样会触发 `WM_CLIPBOARDUPDATE`。

**解法**：写入前开启 1.5 秒"屏蔽窗口"（`Suppress`），监听回调先查 `IsSuppressed`，命中就直接丢弃。
比"bool 标志 + 延时复位"更稳，因为不依赖复位时机。

> 与原始设计文档的差异：`resources/00-原始设计文档.txt` 的示例代码里这个标志叫 `IsSelfCopying`（bool + 延时复位），
> 落地时改成了时间戳方案并更名为 `IsSuppressed`。搜索代码时请用新名字。

**位置**：`Services/ClipboardWriter.cs`（`Suppress`/`IsSuppressed`）、`AppHost.OnClipboardUpdated`

**回归保护**：自检断言「自身写入被标记为屏蔽（防死循环）」。

## 3. CF_DIB 的 alpha 全为 0 → 截图保存后"全透明"

**现象**：Win+Shift+S 截图入库后，缩略图/另存出来是一片透明（或黑底），看起来像图片坏了。

**根因**：Windows 写 CF_DIB 时 alpha 通道通常是垃圾数据（全 0），WPF 会如实按 32bpp 带 alpha 解码，
于是整张图变成全透明。

**解法**：
- 走 DIB/Bitmap 路径的图片统一用 `MakeOpaque()` → `ImageCacheManager.Normalize(source, preserveAlpha: false)`
  把 alpha 全部置 255；
- 走剪切板 `"PNG"` 流路径的图片**保留** alpha（浏览器复制的透明图需要保留）。

**位置**：`Services/ClipboardDataParser.TryReadImage`、`Services/ImageCacheManager.Normalize`

**回归保护**：自检断言「DIB 回读后 alpha 已被修正为不透明」。

## 4. 剪切板取回的位图无法在线程池里编码（真机日志发现）

**现象**：用户实际使用时，**每一次图片入库**日志里都有：

```
[WARN ] 后台保存图片失败，改为同步保存
System.InvalidOperationException: The calling thread cannot access this object because a different thread owns it.
   at System.Windows.Media.Imaging.BitmapFrameDecode.get_InternalMetadata()
```

> 注意日志级别是**定长 5 字符**（`Log.Write` 里写作 `"WARN "`），所以真实行是 `[WARN ]` 而不是 `[WARN]`；
> 用 `Select-String '\[WARN'` 检索即可（`[ERROR]` 是 5 字符，带方括号能直接匹配）。

功能没坏（自动回退到 UI 线程同步保存），但**每次截图都会阻塞 UI 线程**几百毫秒。

**根因**：`BitmapFrame.Create(stream, ..., OnLoad)` 得到的帧，其内部解码器对象仍绑定创建它的
UI 线程；即使已经调用过 `Freeze()`，在线程池线程访问元数据依然抛 `InvalidOperationException`。

**解法**：编码前先在 UI 线程把位图**规范化**成"纯像素的普通 BitmapSource"（`CopyPixels` 到
`byte[]` 再用 `BitmapSource.Create` 重建并 `Freeze`），之后才能安全地交给 `Task.Run`。

**位置**：`Services/ImageCacheManager.Normalize`、`ViewModels/MainViewModel.BuildImageItemAsync`

**回归保护**：自检断言「规范化后的剪切板图片可在后台线程编码」。
**不要**图省事把 `Normalize` 去掉直接 `Task.Run(SavePng)`——这正是修复前的状态。

## 5. 频繁截图导致内存膨胀

**现象**：连续截图后进程内存持续上涨。

**根因**：`BitmapSource`/`BitmapImage` 在 WPF 里很容易持有非托管像素缓冲；列表里每张卡片各存一份全尺寸位图就会失控。

**解法**（三层）：
1. 位图第一时间编码为 PNG 落盘（内容哈希命名，重复内容天然复用同一文件）；
2. 界面只解码 `DecodePixelWidth = 320` 的缩略图，且 `CacheOption=OnLoad`（读完立即释放文件句柄）+ `Freeze()`；
3. 缩略图缓存是**固定容量 LRU（120 条）**，同时卡片列表开启虚拟化（`VirtualizationMode=Recycling`），
   滚出视野的卡片不再持有位图。

**位置**：`Services/ImageCacheManager.cs`、`Views/MainWindow.xaml`（`VirtualizingPanel.*`）

**回归保护**：自检「缩略图已按宽度缩放」「缩略图已冻结」「缩略图缓存可清理」。

## 6. "失焦自动隐藏"和"从外部拖文件进来"互相打架

**现象**：从资源管理器按住文件拖向面板时，面板在鼠标移动到一半就消失了，永远无法拖入。

**根因**：在资源管理器上按下鼠标会让本程序窗口失焦 → 触发隐藏。等光标移到面板位置时窗口已经不见了。

**解法**：失焦时若检测到**鼠标键仍处于按下状态**（`GetAsyncKeyState`），不立即隐藏，而是启动一段
延迟隐藏计时器（默认 700ms，可在设置页「隐藏延迟」里调成 50–1000ms）；计时器到点若鼠标键仍按着就继续等待；
一旦窗口收到 `DragEnter`/`DragOver` 立即取消隐藏。

**位置**：`Views/MainWindow.xaml.cs` → `OnWindowDeactivated`、`OnDeferredHideTick`、
`IsMouseButtonDown`、`OnWindowDragEnter`、`CurrentDeferredHideDelay`（读设置）、`OnSettingsChanged`（实时套用新时长）；
设置项 `DeferredHideDelayMs`（`Services/AppSettings.cs`，默认 700，钳制在 `SettingsService.Normalize`）。

**调延迟为什么不会破坏拖拽**：计时器时长与"拖入取消"是两条独立机制 —— 调小只是让"想收起时收得更快"，
真正防止拖拽被打断的是 `DragEnter/DragOver` 取消与"鼠标键仍按下就继续等待"，两者都与时长无关。

**验证方式**：`tools/ui-flow.ps1` 的 `drag:` 步骤把资源管理器里的文件拖进面板（见第 07 篇）。

### 6.1 姊妹问题：拖出（把卡片拖到别的程序）后没人收尾

**现象**：把卡片拖到资源管理器 / 记事本 / 聊天框并成功放下后，面板不隐藏、一直停在屏幕上。

**根因**：与坑点 6 同源，方向相反。拖入时需要"**别**在拖拽期间隐藏"，拖出时需要"拖拽**结束后**隐藏一次"：

- 拖拽期间窗口失焦会被 `OnWindowDeactivated` 的 `_isDragging` 分支**有意忽略**（否则拖到一半面板就没了）；
- OLE 拖拽循环结束后**不会补发第二次失焦事件** —— 那次被忽略的失焦没有第二次机会。

**解法**：在 `OnListPreviewMouseMove` 里 `DoDragDrop` 返回后补一次收尾：

| 拖拽结束时的状态 | 行为 |
| --- | --- |
| `DragDropEffects != None` 且松手点在面板外（目标程序真的接收了） | `HideAfterDragOut()` → 收起面板（受「失焦即隐藏」开关约束） |
| 效果为 `None`（Esc 取消 / 松在空白处 / 目标不接受） | 保留面板，免得"拖了一下没成"还要重新呼出 |
| 效果为 `Copy` 但松手点仍在面板内 | 保留面板 —— **内部拖拽也会返回 `Copy`**（面板自己是合法放置目标，WPF 把 `allowedEffects` 原样当结果返回），不判位置就会把"手抖拖一下"误当成拖出成功 |

**位置**：`Views/MainWindow.xaml.cs` → `OnListPreviewMouseMove`（拖出分支）、`HideAfterDragOut`、
`IsDropInsidePanel`（`GetCursorPos` + `GetWindowRect`，与窗口定位同一套物理像素口径）。

**验证方式**：`tools/dragout-test.ps1`（六个用例 + 真实鼠标事件，退出码 0/1；停用修复后 `-Mode accept` 会 FAIL）。

> **v1.3.0 补充（多选拖拽）**：多选（拖动已选中的图片 → 一次性拖出整批）**只把 `DoDragDrop` 的入参
> 从单条 `ClipboardItem` 换成集合**，上面这张表里的收尾逻辑**一个字都没动** ——
> `HideAfterDragOut()` / `IsDropInsidePanel()` 及其在 `OnListPreviewMouseMove` 里的调用位置原样保留。
> 以后再加任何"批量输出"都同理：**只换入参、不换收尾**。

**顺带记下的两个实测事实**（自动化脚本里很有用）：拖拽结束后 `Window.IsActive` 仍可能为 `True`
（即使前台已经是别的进程），所以"靠 `!IsActive` 判断要不要隐藏"在真机上并不可靠，判据只能是 `DragDropEffects`；
另外拖拽结束时**光标就停在松手点**，用它判断"有没有拖出面板"是可靠的。

### 6.2 「失焦即隐藏」是**所有**自动收起的总开关

**现象（用户报的原话）**：设置页把「失去焦点时自动隐藏」关掉后，面板还是会自己收起，开关像是没生效。

**根因**：自动收起不止一条路径，而**只有一条**漏了检查开关：

| 自动收起路径 | 触发 | 检查开关 |
| --- | --- | --- |
| `OnWindowDeactivated` | 失焦（鼠标键没按着） | ✅ 一直有 |
| `OnDeferredHideTick` | 失焦时鼠标键按着 → 延迟计时器到点 | ❌ **原先没有**（本次补上） |
| `HideAfterDragOut` | 拖出且目标程序接收 | ✅ 本次新增时就有 |

计时器那条为什么会漏：它由"失焦 + 鼠标键按着"启动，而**启动之后用户完全来得及把开关关掉**
（延迟区间 50–1000ms），到点却无条件收起面板 —— 表现为"开关关了还是隐藏"。

**解法**：每条自动收起在**真正收起之前**都复查一次 `SettingsService.Current.HideOnDeactivate`；
不要只在"启动计时器/开始拖拽"时查一次。

**排查线索（新增）**：
- 切换开关时日志出现 `[设置] 失焦即隐藏 = 开启/关闭` —— 先确认这一行有没有出现，再谈"开关没生效"；
- 拖出成功后日志二选一：`拖出成功，面板已自动隐藏` 或 `拖出成功，但「失焦即隐藏」已关闭，面板保持显示`；
- `MainViewModel.OnPanelShown` 每次呼出都会把开关的真实值推给设置页，界面与内存值不会再各说各话。

**验证方式**：`tools/dragout-test.ps1` 的 `clickaway`（开关开启→点击面板外收起）与
`off`（开关关闭→拖出与点击面板外都保留）两个用例。

> ⚠️ 改这类"开关不生效"的问题前，先确认**跑的是哪份产物**：本项目在多台机器/多个目录各有一份副本时，
> 很容易在 A 目录改、跑 B 目录的 exe（判断依据见 07 篇故障排查表）。

### 6.3 「面板像自己隐藏了」的另一半原因：被**同样置顶**的窗口挡住

**现象**（用户实测反馈）：关掉「失焦即隐藏」后面板明明常驻，可是点了另一个窗口（例如最大化的浏览器、
全屏程序）面板就"不见了"。

**根因**：不是隐藏，是**层级**。面板本来就是 `Topmost`（XAML 写死 + 每次呼出再设一遍），
**普通窗口压不住它**；能压住它的是**同样置顶**的窗口 —— Windows 的规则是
"置顶层里最后被激活的那个在最上面"，所以点一下那个窗口，面板就排到它下面。
实测证据（探针）：点击前"面板中心处最上层窗口"= 面板；点击后变成 `Chrome_WidgetWin_1`（`topmost=True`）。

**解法**：设置项 `KeepOnTopWhenUnfocused`（设置页「始终置顶」，默认关闭，从属于「失焦即隐藏」）：
面板失焦时用 `SetWindowPos(HWND_TOPMOST, SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE)` 抬回置顶层最上方，
再排一次 `DispatcherPriority.Background` 的重复抬升以覆盖对方更晚的 z 序调整。
`SWP_NOACTIVATE` 是关键：**只改层级、不抢焦点**，否则用户点别的窗口会被面板弹回来（回归里专门断言了这条）。

**位置**：`Views/MainWindow.xaml.cs` → `ReassertTopmostIfPinned` / `RaiseTopmost`、
`OnWindowDeactivated`（关掉失焦隐藏的分支）、`ShowPanel`（呼出时也强制抬一次：
`Topmost` 已是 `true`，再赋值不会触发 `SetWindowPos`）。

**验证方式**：`tools/dragout-test.ps1` 的 `ontop` 用例（真实点击一个同样置顶的窗口后，
断言面板回到最上层且前台没被抢）；它的反向对照在 `off` 用例里（没开这个开关时确实会被压住）。

## 7. Fluent 浮层滚动条压住卡片内容

**现象**：设置页每条卡片右边缘被纵向滚动条压住（放大 8 倍可见卡片圆角在滚动条两侧各露一截）；
Emoji 页分类行的横向滚动条横穿胶囊，且末尾分类被裁掉。

**根因**：WPF-UI 的滚动条是**浮在内容之上**的，不会自动挤压内容。
`ScrollViewer.Padding` 在不同控件的模板里行为不一致（ListBox 的 Padding 作用在 ScrollViewer 外层，
ScrollViewer 自身的 Padding 才作用于内容），因此不能依赖它。

**解法**：统一改成**让内容自己留出右侧间距**：

| 位置 | 做法 |
| --- | --- |
| 历史页卡片 | `ClipboardCardStyle.Margin = "0,0,12,7"` |
| 设置页卡片 | `SettingRowStyle.Margin = "0,0,14,6"` |
| Emoji 网格 | `ItemsControl.Margin = "0,0,14,0"` |
| Emoji 分类行 | 横向滚动条改为 `Disabled` + `WrapPanel` 换行（8 个分类两行放得下，根本不需要滚动） |

**位置**：`Themes/Styles.xaml`、`Views/MainWindow.xaml`

**验证方式**：把窗口缩到 380×420 或 498×540 逼出滚动条，再截图放大看右边缘。

## 8. ToolTip 里的中文变成一排方块

**现象**：鼠标停在标题栏"暂停"按钮上，弹出的提示是一串 `▯▯ ▯ ▯▯▯▯▯▯▯`。

**根因**：`CardActionButtonStyle` 把 `FontFamily` 设成了图标字体 `Segoe Fluent Icons`，
而 **ToolTip 会继承所在控件的字体**。图标字体没有中文字形 → 全部渲染成缺字方块。

**解法**：
1. 图标字体从按钮样式里移除，只写在按钮内部的 `TextBlock` 上；
2. 另外加一个全局 `ToolTip` 样式（`Themes/Styles.xaml`），显式指定界面字体 + Fluent 深色外观。

**位置**：`Themes/Styles.xaml`

**注意**：以后给任何控件设 `FontFamily` 前，先想一下它的 ToolTip 会不会跟着变。

## 9. 切到 Emoji 页显示空白

**现象**：在历史页搜索过内容后切到 Emoji 页，Emoji 列表是空的（搜索词被带过去了）。

**根因**：两个页面共用搜索框；`Page` 属性变化时只清理了 Emoji 侧的关键词，没有清空共享搜索框。
另外分页胶囊是直接绑定 `Page` 属性（TwoWay），并不走 `SetPageCommand`，所以命令里的清理逻辑也不会执行。

**解法**：在 `OnPageChanged` 里统一清空搜索框，并把关键词推给 `EmojiViewModel`。
`SetPageCommand` 只保留给托盘菜单等程序化调用。

**⚠️ 同源坑 A（v1.2.0 顶部胶囊改版时踩的，务必记住）**：
`RadioButton.IsChecked` 的绑定与 `Command` **不要同时用**。
给胶囊挂 `Command` 并让 `IsChecked` 走 `OneWay` 时，点击只会改变本地 `IsChecked`（同组互斥由 WPF 处理），
`Command` 并不会像 `Button` 那样被触发 —— 表现为"点了胶囊界面毫无反应"，且不报任何绑定错误。
**不要试图给胶囊加 `Command` 来解决下面的坑 B**，那样只会换一种方式失效。

**⚠️ 同源坑 B（"进设置后再点全部，停在设置页不动"）**：
**别把"切换页面"只挂在属性 setter 的变更通知上**。
`OnFilterChanged` 只在 `Filter` 的**值真的变了**才触发；而用户进设置页后点「全部」时
`Filter` 本来就是 `All`（没有变化）→ 回调不执行 → 页面不切，界面看起来"点了没反应"。
（点「文本」这类会改变 `Filter` 的胶囊则正常，所以这个 Bug 只在跨页点"当前已选中"的筛选时出现。）

**解法**：把页面/筛选的落地放到胶囊的 `Checked` **事件**上（`Views/MainWindow.xaml` 的
`Checked="OnMainChipChecked"` + `Tag` 标明目标），因为"被选中"这个动作本身总是可靠的；
顺序固定为**先切回历史页、再设筛选**。保留 `IsChecked` 双向绑定负责选中态展示，
并用 `_chipClickInProgress` 挡掉"设置属性 → 反向改 IsChecked"的重入。
`OnFilterChanged` 里的回切历史页保留作为程序化调用的兜底。

**位置**：`ViewModels/MainViewModel.cs` → `OnPageChanged`、`OnFilterChanged`；
`Views/MainWindow.xaml`（顶部胶囊的 `Tag` / `Checked`）、`Views/MainWindow.xaml.cs` → `OnMainChipChecked`

**验证方式**：设置页 → 点「全部」必须回到历史列表（v1.2.1 起「全部」= 全部未收藏记录，收藏项只在 ⭐ 里）；
Emoji 页 → 点「文本」必须回到历史列表且只剩未收藏的文本条目
（可用 UI Automation 选中胶囊后截图核对）。

## 10. 单文件发布让常驻内存翻倍

**现象**：同一个程序，单文件版空载工作集 ≈260MB（v1.1.0 重新实测，明细见项目根 README 的「发布方式与内存占用」），框架依赖版 ≈120MB。

**根因**：单文件发布时，托管程序集是从 bundle 读入内存加载的（而非文件映射），这部分私有内存明显更高。
属于 .NET 单文件发布的固有代价，**不是内存泄漏**（实测空载再等 10 秒无增长：258.1 → 258.0 MB，见项目根 README）。

**解法**：不修改代码；在 README 里给出三种发布方式的体积/内存对比，让使用者按需选择。
若在意常驻内存，用 `-p:PublishSingleFile=false`（自包含多文件）或框架依赖方式发布。

## 12. 无法把内容粘贴到"以管理员身份运行"的程序

## 14. WPF 不支持彩色字体 → Emoji 只能单色

**位置**：`Themes/Styles.xaml`（`EmojiButtonStyle`、`EmojiFont`）

**若要彩色**：见 [08-后续开发路线.md](08-后续开发路线.md) 的方案对比。

## 17. Win+V 接管：钩子回调的三条红线 + 抢焦点的两个坑

**位置**：`Services/KeyboardHookService.cs`、`Views/MainWindow.xaml.cs` → `EnsureForeground` / `_showInProgress`、`Services/PasteService.cs` → `ForceForeground`

### 17.1 低级钩子回调的三条红线

1. **不能阻塞**：Windows 对 `WH_KEYBOARD_LL` 回调有 `LowLevelHooksTimeout`（默认 300ms）限制，
   超时未 return 会被系统直接卸载钩子（表现为"用一会儿就失灵"）。
   所以回调里只做：判定 Win 状态 → 注入哑键 → `Dispatcher.BeginInvoke` 异步唤起 → `return 1`。
2. **委托必须强引用**：`_hookProc` 存成字段，否则 GC 回收后原生侧回调 → `CallbackOnCollectedDelegate` 崩溃。
3. **异常不许逃逸**：回调里 `try/catch` 全包，异常穿到原生栈会直接终止进程。

配套细节：`_winVHandled` 抑制长按 V 的自动重复（否则面板疯狂开关）；`_injecting` 防止自己注入的
哑键再次进入判定逻辑。

### 17.2 哑键为什么必须有

返回 1 把 V 键摘掉后，Shell 仍认为"Win 键被单独按了一下"，松开 Win 时会弹开始菜单。
注入一次无功能的 `VK_NONAME (0xFC)` 让 Shell 认定 Win 参与了组合键，从根上避免弹菜单
（AutoHotkey 的 `A_MenuMaskKey` 是同一思路）。

### 17.3 `Activate()` 会被前台锁定驳回

**现象**：Win+V 唤起后，面板浮在最上层，但键盘输入还在原来的窗口里（打不了字）。

**根因**：由低级钩子唤起时，本进程并不是"最后接收输入的进程"，`SetForegroundWindow` 被前台锁定规则驳回；
而 `PasteService.ActivateWindow` 的 `AttachThreadInput` 兜底对自己人无效 —— 目标窗口就是自己的线程，
`targetThread == currentThread` 直接返回 false。

**解法**：`PasteService.ForceForeground` 改为把当前线程挂到**当前前台窗口所在线程**的输入队列上再抢，
最后用 `BringWindowToTop` + `SetWindowPos(HWND_TOPMOST)` 兜底；`MainWindow.EnsureForeground` 以
`GetForegroundWindow()` 的实际值判断（WPF 的 `IsActive` 此时可能是 true），并在延时聚焦回调里复查一次。
管理员权限的前台窗口受 UIPI 限制仍抢不到，只能记警告。

### 17.4 抢焦点会触发"失焦即隐藏"

**现象**：面板弹出来一瞬间就消失（窗口其实还在，只是不可见）。

**根因**：抢前台过程中系统会先送一个 `WM_ACTIVATE(INACTIVE)`，触发 `OnWindowDeactivated` →
`HideOnDeactivate` 直接把刚显示的窗口 `Hide()` 了（此时抢焦点恰好成功，于是出现"隐藏窗口却是前台窗口"的怪状态）。

**解法**：`ShowPanel` 期间置 `_showInProgress = true`，`OnWindowDeactivated` 见到该标记直接返回；
延时聚焦回调（`DispatcherPriority.Input`）里复位。`HidePanel` 也会复位，防止标记泄漏。

### 17.5 真机验收结论（2026-09-19）

Release v1.1.0 在 Win11 23H2（原生剪切板历史开启）上人工核对：按 Win+V → 系统面板不再弹出、
本面板弹出且可直接打字搜索；再按一次收起；Ctrl+Shift+V 与其余主体功能均无回归。
`tools/winv-test.ps1` 只能自动核对"钩子命中 / 面板弹出 / 抢到焦点 / 开关语义"，
原生面板是否被压住必须真机手按（注入输入不触发 Shell 的剪切板历史）。

> **后续变更（v1.2.2）**：上面那句"可直接打字搜索"只对 v1.2.1 及更早成立。
> 现在呼出后光标不再落在搜索框（焦点交给窗口本身），搜索用 Ctrl+F 或点击进入 ——
> 这条链路该验的是"面板弹出 + 抢到前台焦点"，与搜索框焦点无关，故 `winv-test.ps1` 无需改动。

> **最容易踩的一次**：改完代码后仍启动旧目录的 exe（Debug 编好了却在跑 Release 的旧产物），
> 现象与"功能没生效"完全一样。定位口诀：**先看设置页「关于」的版本号，再看日志里有没有
> `[KeyboardHookService] 已挂载低级键盘钩子`**。

## 18. 设置行的说明文字折进右对齐的开关底下

**现象**：设置页「始终置顶」那一行的说明被开关盖住半行 —— 第一行末尾的"自动抬"只剩半个字，
看着像被斜着削掉；开关置灰（`IsEnabled=False`）时更糊，灰色图元叠在灰字上、文字像直接没了。
用户截图（467×696，深色主题）里一眼可见。

**根因**：**同一个 `Grid` 单元格里一个左对齐、一个右对齐，两者都不给对方让位**。
「标题 + 说明」的 `StackPanel` 因此拿到整行宽度（@470 窗口宽实测 **402px**），
而右对齐的 `ToggleSwitch` 占的是同一片空间的右侧 40px（@470 实测 X=389..429）：
文字**按 402px 换行**，于是最后几个字排到了开关底下。也就是说开关不是"挤开"了文字，
而是**压在**文字上。这是坑点 13（窄窗口重叠）的同族问题，区别是触发条件不是窗口窄，
而是**说明文案够长** —— 短文案行同样拿到 402px 宽，只是拐不到开关下面就看不出来。

> ⚠️ 这条坑的**可见性取决于折行落在哪**，排查时别被"某次量下来没压上"骗了：
> 同一份代码，同一个 467×696，实测「文字右沿」在 **−39px（明显压上）** 与 **+1px（刚好擦过）**
> 之间跳 —— 取决于这一行最后一行排到哪个字、以及当时的窗口宽度差几像素。
> 也就是说它**不是"某个尺寸才有的问题"，而是"迟早会压上"的排版缺陷**；
> 用户截图抓到的是压上的那一次。判断这类问题要看**结构**（标题列有没有给开关留出宽度），
> 而不是只看某次截图的像素。

**解法**：给标题这一列留出开关的宽度，并提成样式（避免下一个人再手写、漏写）：

```xml
<!-- Themes/Styles.xaml -->
<Style x:Key="SettingRowLabelStyle" TargetType="StackPanel">
    <Setter Property="Margin" Value="0,0,56,0" />   <!-- 40 开关 + 16 间隔 -->
</Style>
```

设置页里凡是有"右对齐开关"的行，标题列一律 `Style="{StaticResource SettingRowLabelStyle}"`。
`56` 与「Win+V 拦截」行原先手写的 `Margin="0,0,56,0"` 是同一个值 —— 那一行本来就没问题，
本次把它提成样式，并补上漏写的「始终置顶」行。将来改开关宽度只需改这一处。

**位置**：`Themes/Styles.xaml`（`SettingRowLabelStyle`）、`Views/MainWindow.xaml`
（「始终置顶」「Win+V 拦截」两行的标题 `StackPanel`）

**验证方式**：`tools/settings-layout-test.ps1`（把窗口尺寸写进 `settings.json` 再重启，
逐档核对 470 / 467 两种宽度 ×「始终置顶」可用 / 置灰两种状态），两条判据都要过：

| 判据 | 说明 | 修复前 | 修复后 |
| --- | --- | --- | --- |
| 结构 | 标题列的**排版宽度**整体避开开关（列右沿 → 开关左沿 ≥ 8px） | **−40px**（列宽 = 整行） | **+16px**（列宽 402 → 346） |
| 像素 | 真正画出来的字不压到开关（逐行从右往左找第一个非背景像素） | **+1px**（擦着开关） | **+19…22px** |

- 脚本在这份改动上做过**反向对照**：把 `SettingRowLabelStyle` 从「始终置顶」行撤掉重建，
  立刻 8 项 FAIL、退出码 1；装回去 0 项 FAIL —— 证明它不是永远绿的摆设。
- ⚠️ **别用"文字块宽度"直接当"压没压上"的判据**：文字块宽度**永远是整行宽**（402px），
  那正是坑点本身；能反映问题的量是"**排版后的列宽**"（= 402 − 56）与"**实际画到哪**"。
  另外按"矩形相交"批量扫描会把「点击卡片后自动粘贴」这类**短文案行**全部误报成重叠 ——
  脚本因此只对"自然宽度够得着开关"的行（长文案行）提结构要求。

## 19. "把剪切板整份存下来、用完再写回去"的三个坑（v1.2.4）

**背景**：面板输出（点卡片自动粘贴）现在只把系统剪切板"借"一次 —— 写之前抓快照，粘贴送达后 300ms 还原，
这样按 Ctrl+V 拿到的仍是列表顶部那条（需求原话见 [CHANGELOG v1.2.4](CHANGELOG.md)）。
抓快照这件事看着简单，实际踩了三个坑，全部有真机证据。

### 19.1 字节型格式不能走"字符串通道"

`Clipboard.GetDataObject()` 会把 **HTML Format / Rich Text Format 也当成字符串**读出来，
但这两个格式在剪切板上的载荷其实是 **UTF-8 / ANSI 字节**。用 `DataObject.SetData(format, string)` 写回去等于改名换姓：

| 格式 | 原始载荷 | 字符串通道往返后 | 原始 HGLOBAL 字节往返后 |
| --- | --- | --- | --- |
| `HTML Format` | 196 字节（UTF-8） | 196 字节，**末尾被补一个 NUL** | **逐字节一致** |
| `Rich Text Format` | 69 字节（UTF-8） | **1 字节**（整段被吃成空串） | **逐字节一致** |
| `PNG` | 140 字节 | 140 字节（WPF 给的是流，本来就走字节） | **逐字节一致** |

- **解法**：只把 `UnicodeText` / `Text` / `OEMText` 交给字符串通道，其余（含 HTML / RTF）一律
  用 `OpenClipboard` + `GetClipboardData` + `GlobalSize/GlobalLock` 抓**原始 HGLOBAL 字节**，
  写回时包成 `MemoryStream`（`ClipboardWriter.CaptureFormat` 的分支顺序就是这么定的）。
- **验证**：`--selftest` 的「多格式：HTML Format 逐字节一致」用 Win32 原始字节读回比对；
  结论出自一个不入库的探针工程（逐格式打印 `GetFormats(autoConvert:false)` 与 `GetData` 的返回类型）。

### 19.2 `RawBytes` 载荷必须统一成 `byte[]`

同一个 `SnapshotPayload.RawBytes` 分支会有两个来源：**流格式**（`MemoryStream`）与 **HGLOBAL 字节**（`byte[]`）。
还原侧按 `byte[]` 写回时，前者会抛：

```
System.InvalidCastException: Unable to cast object of type 'System.IO.MemoryStream' to type 'System.Byte[]'.
```

表现极具误导性：日志里"快照存下了""粘贴已送达，将安排还原"都在，**只有剪切板没变回去**（还原后是 `[WARN ] 还原剪切板失败`）。
- **解法**：捕获侧统一 `.ToArray()`（`CopyStream` 返回 `byte[]`），别在还原侧做类型判断 —— 那种"两种类型都兼容"的写法
  下次加第三种载荷时还会再踩一次。
- **这条是自检先漏、真机端到端抓到的**：自检原来的用例只有纯文本与 HTML，压根没有流格式；
  现已补「图片（位图 + PNG 流）」两条载荷做回归保护（`tools/restore-clipboard-test.ps1` 第一次跑就命中了它）。

### 19.3 GDI 句柄类格式不能按 HGLOBAL 强读

`CF_BITMAP` / `CF_PALETTE` / `CF_METAFILEPICT` 给的是 **GDI 句柄**，不是全局内存块。
对它调 `GlobalSize` / `GlobalLock` 拿到的是垃圾甚至 0，照抄进快照再写回就是往剪切板里塞一段坏数据。
- **解法**：先 `GlobalFlags(handle) == GMEM_INVALID_HANDLE` 判定，读不到就**跳过该格式**（记一行 Info），
  位图另有 WPF 的通道负责（`GetData(DataFormats.Bitmap)` → `BitmapSource` → 写回用 `SetImage`，
  由 WPF 生成正确的 DIB / BITMAP 载荷）。探针实测：`CF_BITMAP` 的 `GlobalSize` 读回 −1（保护生效）。

## 20. 多选图片的手势分派（v1.3.0）

「Ctrl / Shift + 左键选几张图片，拖动其中任意一张把整批拖出去」这个功能的风险**全部集中在
手势起点判定那一处**：写错了不会崩、不会报错，只会"看起来选了、拖出去却只有一张"或者
"Ctrl+点一下顺手粘贴了一次"。下面是落地时踩过 / 差点踩到的五条。

### 20.1 修饰键只能在 MouseDown 时读一次（快照），不能到 MouseUp 再读

**现象**：按住 Ctrl 点一张图片、**松开鼠标左键之前先把 Ctrl 松开**，这一次点击被当成"普通单击" ——
多选被清空、并且**顺手把这张图复制粘贴了一次**（面板也收起了）。

**根因**：`Keyboard.Modifiers` 读的是"此刻"的键盘状态，而用户完全可能在按住鼠标的这段时间里松开修饰键。
判定"这次点击是选择还是激活"必须用**按下鼠标那一刻**的状态。

**解法**：`OnListPreviewMouseLeftButtonDown` 里存一份快照 `_gestureModifiers = Keyboard.Modifiers`，
`OnListPreviewMouseLeftButtonUp` 只按这份快照分派（Ctrl → 切换单张 / Shift → 区间 / 都没有 → 原激活路径）。

**验证方式**：`tools/multidrag-test.ps1 -Mode modsnapshot`
（"按下 Ctrl → 先松 Ctrl → 再松鼠标"：仍是选择手势、面板不收、剪切板内容原样）。

### 20.2 `PreviewMouseLeftButtonUp` 里**不要**设 `e.Handled = true`

`OnListPreviewMouseLeftButtonUp` 是**隧道**事件（挂在 ListBox 上）。在这里把事件标记为已处理，
`ListBoxItem` 就收不到自己的 `MouseLeftButtonUp`（它在那里 `ReleaseMouseCapture()`），
可能留下**未释放的鼠标捕获**，把后面的点击一起弄坏 —— 症状是"点了几次之后列表就点不动了"。
选择手势本身不需要吞事件：`ListBox` 的选中在 MouseDown 阶段就已经做完了（见 20.3）。

### 20.3 `SelectionMode` 保持默认的 `Single`（**不要**改成 `Extended`）

实施方案原本建议给 `HistoryList` 加 `SelectionMode="Extended"`，理由是"预览事件已 `e.Handled`
所以不会和 WPF 自己的选择打架"。这个理由**不成立**：`ListBox` 的选中发生在
`MouseLeftButtonDown`（冒泡）阶段，早于我们处理 `PreviewMouseLeftButtonUp`。

加了 `Extended` 之后：

- Shift+点击会让 `ListBox` 把**区间内的所有卡片**（含文本 / 文件）都标成 `IsSelected`，
  于是它们也会被画上 1px 强调色"当前项"边框 —— 看起来像被选中了，与"多选仅对图片生效"直接矛盾；
- Ctrl+再点一次同一张会取消它的"当前项"状态（`SelectedItem` 变 null），Enter / Delete 随之失去目标。

**结论**：多选状态**只**由 `ClipboardSelection` 表达，`ListBox` 自己的选择依旧只表示"键盘光标在哪张卡"。
（自检与端到端脚本都不依赖 `SelectionMode`。）

### 20.4 多选起点按 `Items` 的 **index** 算；Shift 范围里锚点必须"先存后恢复"

- `HistoryList` 开了虚拟化（`IsVirtualizing=True` + `Recycling`），**没实例化的卡片不在可视化树里**，
  按可视化树算范围必然错（与 07 篇 `pin-filter-test` 的三条要点同源）。
  `ClipboardSelection` 因此只认 `Items.IndexOf`；
- `SelectRangeImages` 里有一处容易写错的地方：清空旧选择用的 `ClearCore()` **会顺手把锚点置空**，
  而"连续多次 Shift 点击以同一个锚点为基准反复调整范围"正需要锚点活着 ——
  所以必须**先存 `_anchor`、清空后写回**。漏了这一步的表现是"第二次 Shift 点击退化成只选一张"，
  界面不报错（自检「锚点被取消后回退到剩余已选项」与端到端 `-Mode shift` 都盯着它）。

### 20.5 Ctrl / Shift 按住时"不启动拖拽"的守卫必须放在**位移判定之前**

修饰键手势的语义是"选择"，不是"拖出"。守卫若放在位移判定之后，`_dragMoved` 已经被置为 true，
松手时的 MouseUp 分支会直接 return —— 表现是"Ctrl+点住稍微一动，这次选择就没了（也不拖）"。
放在位移判定之前，手势被干净地分成三种：**修饰键+点击 = 选择、无修饰键+点击 = 激活、
无修饰键+拖动 = 拖出**，`DoDragDrop` 的收尾逻辑一个字都不用改。

**验证方式**：`tools/multidrag-test.ps1 -Mode nodrag`（Ctrl 按住拖动：目标什么都没收到、面板保留、
剪切板内容原样）。

### 20.6 Ctrl+点击非图片时"拒绝"而不是"清空"

Ctrl+点到文本 / 文件卡片时，正确行为是**不改变已有选择**并给一条提示条（`多选仅支持图片`）。
顺手清空看起来更"简洁"，但用户在一串图片里误点一张文本，代价是前面选的全没了。

## 已知边界：高权限（以管理员运行）的前台窗口

> 📄 **本节的完整版（定位过程、代码级实测手段、4 个备选方案与代价对比、将来动手的落地要点）
> 已独立成篇：[10-高权限窗口支持决策记录.md](10-高权限窗口支持决策记录.md)。**
> 只想快速了解结论看本节即可；要动这块代码请先读第 10 篇。

**现象**：在**以管理员权限运行**的程序（例如 `run_as_admin=1` 的 Everything）里，按 Win+V 不会唤起本面板，
只会弹出系统原生剪切板；从那类窗口往面板拖文件时面板也会中途隐藏。

**根因**：Windows 的 UIPI（用户界面特权隔离）。实测（独立探针 A/B/C 三组对照，`WH_KEYBOARD_LL` 钩子）：

| 前台窗口 | 钩子是否收到按键 |
| --- | --- |
| 与钩子进程同级（HIGH ↔ HIGH） | ✔ 收到 |
| 高一级（Everything=HIGH，钩子进程=MEDIUM） | ✘ 完全收不到 |
| 高一级窗口最小化后 | ✔ 恢复收到 |

即：**低于前台窗口完整性级别的进程，其低级键盘钩子回调会被系统直接丢弃**，
所以 Win+V 根本到不了本程序，而是原样落给 Shell 的原生剪切板历史。
同理，非提权进程也无法从提权窗口手里抢回前台焦点（`EnsureForeground` 会记
`面板未能取得前台焦点（前台窗口可能以管理员权限运行）`），拖拽因此更难完成。

**当前处置（v1.2.0 决策）**：不修改架构，作为已知边界记录。可选的规避方式：

1. 让那个程序不再以管理员权限运行（Everything：选项里取消"以管理员身份运行"）——零代码改动，最有效；
2. 需要长期支持时，业界标准做法是再引入一个**以管理员权限常驻的轻量钩子进程**（首次启动需一次 UAC），
   由它挂钩并通过 IPC 通知主程序。代价是新增进程/生命周期/IPC 管理，属于架构级改动，
   并会牵出"自动粘贴到管理员窗口"等既有 UIPI 限制。

**顺带实测**：`RegisterHotKey(MOD_WIN, V)` 在本机返回 1409（`ERROR_HOTKEY_ALREADY_REGISTERED`）——
原生剪切板历史占用了这个热键，所以"改用全局热键代替钩子"这条路走不通，
除非关掉原生剪切板历史（`HKCU\Software\Microsoft\Clipboard\EnableClipboardHistory=0` 并重新登录，
本次实测重启 explorer 后该键仍被占用）。
