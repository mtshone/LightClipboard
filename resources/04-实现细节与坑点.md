# 04 · 实现细节与坑点

本文档记录**真机上踩过的坑**：现象 → 根因 → 解法 → 代码位置。
改剪切板、图片、拖拽、面板显隐相关代码前请先读一遍；末尾的「不可回退清单」请勿删除。

---

## 1. 剪切板被其他程序独占（CLIPBRD_E_CANT_OPEN）

**现象**：偶发读不到剪切板内容，日志出现 `读取剪切板失败: ... CLIPBRD_E_CANT_OPEN`，那条复制记录丢失。

**根因**：剪切板是全局共享资源。别的程序正在 `OpenClipboard`/写入时，本进程的 `Clipboard.GetText()` 会抛
`COMException`。

**解法**：整个"读取 + 解析"包在退避重试里：最多 3 次，间隔 50ms / 100ms / 150ms。

**位置**：`Services/ClipboardDataParser.cs` → `TryRead` / `ReadCore`

**回归保护**：自检分组「剪切板读写（文本 / Emoji / 图片）」。

## 2. 自身写入剪切板导致的死循环

**现象**：点击卡片"复制到剪切板"后，该条记录又被当成新内容重新入库（时间戳反复刷新，甚至列表跳动）。

**根因**：本程序写剪切板同样会触发 `WM_CLIPBOARDUPDATE`。

**解法**：写入前开启 1.5 秒"屏蔽窗口"（`Suppress`），监听回调先查 `IsSuppressed`，命中就直接丢弃。
比"bool 标志 + 延时复位"更稳，因为不依赖复位时机。

> 与原始设计文档的差异：`resources/00-原始设计文档.txt` 的示例代码里这个标志叫 `IsSelfCopying`（bool + 延时复位），
> 落地时改成了时间戳方案并更名为 `IsSuppressed`。搜索代码时请用新名字。

**位置**：`Services/ClipboardWriter.cs`（`Suppress`/`IsSuppressed`）、`AppHost.OnClipboardUpdated`

**回归保护**：自检断言「自身写入被标记为屏蔽（防死循环）」。

## 3. CF_DIB 的 alpha 全为 0 → 截图保存后"全透明"

**现象**：Win+Shift+S 截图入库后，缩略图/另存出来是一片透明（或黑底），看起来像图片坏了。

**根因**：Windows 写 CF_DIB 时 alpha 通道通常是垃圾数据（全 0），WPF 会如实按 32bpp 带 alpha 解码，
于是整张图变成全透明。

**解法**：
- 走 DIB/Bitmap 路径的图片统一用 `MakeOpaque()` → `ImageCacheManager.Normalize(source, preserveAlpha: false)`
  把 alpha 全部置 255；
- 走剪切板 `"PNG"` 流路径的图片**保留** alpha（浏览器复制的透明图需要保留）。

**位置**：`Services/ClipboardDataParser.TryReadImage`、`Services/ImageCacheManager.Normalize`

**回归保护**：自检断言「DIB 回读后 alpha 已被修正为不透明」。

## 4. 剪切板取回的位图无法在线程池里编码（真机日志发现）

**现象**：用户实际使用时，**每一次图片入库**日志里都有：

```
[WARN ] 后台保存图片失败，改为同步保存
System.InvalidOperationException: The calling thread cannot access this object because a different thread owns it.
   at System.Windows.Media.Imaging.BitmapFrameDecode.get_InternalMetadata()
```

> 注意日志级别是**定长 5 字符**（`Log.Write` 里写作 `"WARN "`），所以真实行是 `[WARN ]` 而不是 `[WARN]`；
> 用 `Select-String '\[WARN'` 检索即可（`[ERROR]` 是 5 字符，带方括号能直接匹配）。

功能没坏（自动回退到 UI 线程同步保存），但**每次截图都会阻塞 UI 线程**几百毫秒。

**根因**：`BitmapFrame.Create(stream, ..., OnLoad)` 得到的帧，其内部解码器对象仍绑定创建它的
UI 线程；即使已经调用过 `Freeze()`，在线程池线程访问元数据依然抛 `InvalidOperationException`。

**解法**：编码前先在 UI 线程把位图**规范化**成"纯像素的普通 BitmapSource"（`CopyPixels` 到
`byte[]` 再用 `BitmapSource.Create` 重建并 `Freeze`），之后才能安全地交给 `Task.Run`。

**位置**：`Services/ImageCacheManager.Normalize`、`ViewModels/MainViewModel.BuildImageItemAsync`

**回归保护**：自检断言「规范化后的剪切板图片可在后台线程编码」。
**不要**图省事把 `Normalize` 去掉直接 `Task.Run(SavePng)`——这正是修复前的状态。

## 5. 频繁截图导致内存膨胀

**现象**：连续截图后进程内存持续上涨。

**根因**：`BitmapSource`/`BitmapImage` 在 WPF 里很容易持有非托管像素缓冲；列表里每张卡片各存一份全尺寸位图就会失控。

**解法**（三层）：
1. 位图第一时间编码为 PNG 落盘（内容哈希命名，重复内容天然复用同一文件）；
2. 界面只解码 `DecodePixelWidth = 320` 的缩略图，且 `CacheOption=OnLoad`（读完立即释放文件句柄）+ `Freeze()`；
3. 缩略图缓存是**固定容量 LRU（120 条）**，同时卡片列表开启虚拟化（`VirtualizationMode=Recycling`），
   滚出视野的卡片不再持有位图。

**位置**：`Services/ImageCacheManager.cs`、`Views/MainWindow.xaml`（`VirtualizingPanel.*`）

**回归保护**：自检「缩略图已按宽度缩放」「缩略图已冻结」「缩略图缓存可清理」。

## 6. "失焦自动隐藏"和"从外部拖文件进来"互相打架

**现象**：从资源管理器按住文件拖向面板时，面板在鼠标移动到一半就消失了，永远无法拖入。

**根因**：在资源管理器上按下鼠标会让本程序窗口失焦 → 触发隐藏。等光标移到面板位置时窗口已经不见了。

**解法**：失焦时若检测到**鼠标键仍处于按下状态**（`GetAsyncKeyState`），不立即隐藏，而是启动一段
延迟隐藏计时器（默认 700ms，可在设置页「隐藏延迟」里调成 50–1000ms）；计时器到点若鼠标键仍按着就继续等待；
一旦窗口收到 `DragEnter`/`DragOver` 立即取消隐藏。

**位置**：`Views/MainWindow.xaml.cs` → `OnWindowDeactivated`、`OnDeferredHideTick`、
`IsMouseButtonDown`、`OnWindowDragEnter`、`CurrentDeferredHideDelay`（读设置）、`OnSettingsChanged`（实时套用新时长）；
设置项 `DeferredHideDelayMs`（`Services/AppSettings.cs`，默认 700，钳制在 `SettingsService.Normalize`）。

**调延迟为什么不会破坏拖拽**：计时器时长与"拖入取消"是两条独立机制 —— 调小只是让"想收起时收得更快"，
真正防止拖拽被打断的是 `DragEnter/DragOver` 取消与"鼠标键仍按下就继续等待"，两者都与时长无关。

**验证方式**：`tools/ui-flow.ps1` 的 `drag:` 步骤把资源管理器里的文件拖进面板（见第 07 篇）。

## 7. Fluent 浮层滚动条压住卡片内容

**现象**：设置页每条卡片右边缘被纵向滚动条压住（放大 8 倍可见卡片圆角在滚动条两侧各露一截）；
Emoji 页分类行的横向滚动条横穿胶囊，且末尾分类被裁掉。

**根因**：WPF-UI 的滚动条是**浮在内容之上**的，不会自动挤压内容。
`ScrollViewer.Padding` 在不同控件的模板里行为不一致（ListBox 的 Padding 作用在 ScrollViewer 外层，
ScrollViewer 自身的 Padding 才作用于内容），因此不能依赖它。

**解法**：统一改成**让内容自己留出右侧间距**：

| 位置 | 做法 |
| --- | --- |
| 历史页卡片 | `ClipboardCardStyle.Margin = "0,0,12,7"` |
| 设置页卡片 | `SettingRowStyle.Margin = "0,0,14,6"` |
| Emoji 网格 | `ItemsControl.Margin = "0,0,14,0"` |
| Emoji 分类行 | 横向滚动条改为 `Disabled` + `WrapPanel` 换行（8 个分类两行放得下，根本不需要滚动） |

**位置**：`Themes/Styles.xaml`、`Views/MainWindow.xaml`

**验证方式**：把窗口缩到 380×420 或 498×540 逼出滚动条，再截图放大看右边缘。

## 8. ToolTip 里的中文变成一排方块

**现象**：鼠标停在标题栏"暂停"按钮上，弹出的提示是一串 `▯▯ ▯ ▯▯▯▯▯▯▯`。

**根因**：`CardActionButtonStyle` 把 `FontFamily` 设成了图标字体 `Segoe Fluent Icons`，
而 **ToolTip 会继承所在控件的字体**。图标字体没有中文字形 → 全部渲染成缺字方块。

**解法**：
1. 图标字体从按钮样式里移除，只写在按钮内部的 `TextBlock` 上；
2. 另外加一个全局 `ToolTip` 样式（`Themes/Styles.xaml`），显式指定界面字体 + Fluent 深色外观。

**位置**：`Themes/Styles.xaml`

**注意**：以后给任何控件设 `FontFamily` 前，先想一下它的 ToolTip 会不会跟着变。

## 9. 切到 Emoji 页显示空白

**现象**：在历史页搜索过内容后切到 Emoji 页，Emoji 列表是空的（搜索词被带过去了）。

**根因**：两个页面共用搜索框；`Page` 属性变化时只清理了 Emoji 侧的关键词，没有清空共享搜索框。
另外分页胶囊是直接绑定 `Page` 属性（TwoWay），并不走 `SetPageCommand`，所以命令里的清理逻辑也不会执行。

**解法**：在 `OnPageChanged` 里统一清空搜索框，并把关键词推给 `EmojiViewModel`。
`SetPageCommand` 只保留给托盘菜单等程序化调用。

**⚠️ 同源坑 A（v1.2.0 顶部胶囊改版时踩的，务必记住）**：
`RadioButton.IsChecked` 的绑定与 `Command` **不要同时用**。
给胶囊挂 `Command` 并让 `IsChecked` 走 `OneWay` 时，点击只会改变本地 `IsChecked`（同组互斥由 WPF 处理），
`Command` 并不会像 `Button` 那样被触发 —— 表现为"点了胶囊界面毫无反应"，且不报任何绑定错误。
**不要试图给胶囊加 `Command` 来解决下面的坑 B**，那样只会换一种方式失效。

**⚠️ 同源坑 B（"进设置后再点全部，停在设置页不动"）**：
**别把"切换页面"只挂在属性 setter 的变更通知上**。
`OnFilterChanged` 只在 `Filter` 的**值真的变了**才触发；而用户进设置页后点「全部」时
`Filter` 本来就是 `All`（没有变化）→ 回调不执行 → 页面不切，界面看起来"点了没反应"。
（点「文本」这类会改变 `Filter` 的胶囊则正常，所以这个 Bug 只在跨页点"当前已选中"的筛选时出现。）

**解法**：把页面/筛选的落地放到胶囊的 `Checked` **事件**上（`Views/MainWindow.xaml` 的
`Checked="OnMainChipChecked"` + `Tag` 标明目标），因为"被选中"这个动作本身总是可靠的；
顺序固定为**先切回历史页、再设筛选**。保留 `IsChecked` 双向绑定负责选中态展示，
并用 `_chipClickInProgress` 挡掉"设置属性 → 反向改 IsChecked"的重入。
`OnFilterChanged` 里的回切历史页保留作为程序化调用的兜底。

**位置**：`ViewModels/MainViewModel.cs` → `OnPageChanged`、`OnFilterChanged`；
`Views/MainWindow.xaml`（顶部胶囊的 `Tag` / `Checked`）、`Views/MainWindow.xaml.cs` → `OnMainChipChecked`

**验证方式**：设置页 → 点「全部」必须回到完整历史列表；Emoji 页 → 点「文本」必须回到历史列表且只剩文本条目
（可用 UI Automation 选中胶囊后截图核对）。

## 10. 单文件发布让常驻内存翻倍

**现象**：同一个程序，单文件版空载工作集 ≈270MB，框架依赖版 ≈120MB。

**根因**：单文件发布时，托管程序集是从 bundle 读入内存加载的（而非文件映射），这部分私有内存明显更高。
属于 .NET 单文件发布的固有代价，**不是内存泄漏**（实测空载 20 秒前后无增长）。

**解法**：不修改代码；在 README 里给出三种发布方式的体积/内存对比，让使用者按需选择。
若在意常驻内存，用 `-p:PublishSingleFile=false`（自包含多文件）或框架依赖方式发布。

**位置**：`LightClipboard.csproj`（Release 段）、`README.md`

## 12. 无法把内容粘贴到"以管理员身份运行"的程序

**现象**：目标程序是管理员权限时，点卡片后剪切板内容更新了，但没粘上去。

**根因**：Windows 的 UIPI（用户界面特权隔离）会拦截低完整性进程向高完整性窗口注入的按键
（`SendInput`）。本程序以 `asInvoker` 运行（`app.manifest`），不会主动提权。

**可行的规避**：此时用"只复制不粘贴"（卡片上的复制按钮，或关闭设置里的自动粘贴）再手动 Ctrl+V。
若确实需要注入管理员窗口，本程序必须以管理员身份运行——但那会导致普通程序无法与它交互剪切板，
**不建议**修改 manifest。

**位置**：`app.manifest`、`Services/PasteService.cs`

## 13. 窄窗口下控件互相重叠

**现象**：把面板拖窄后，页脚提示文字压在「清空/隐藏」按钮下面；分页胶囊与筛选胶囊挤在一起。

**根因**：两组控件放在同一 `Grid` 单元格里（一个左对齐一个右对齐），空间不足时直接重叠。

**解法**：
- 页脚改两列布局（`*` + `Auto`），文本加 `TextTrimming="CharacterEllipsis"`；
- 顶部胶囊（v1.2.0 起是「全部/文本/图片/文件/Emoji/★/设置」一条主链）用**单个 `WrapPanel`** 承载，
  空间不足时自动换行，不再有两组控件互相挤占的问题。

**位置**：`Views/MainWindow.xaml`（页脚 Grid、顶部胶囊 WrapPanel）

**验证方式**：窗口缩到 380×420 截图检查；默认 470 宽下 7 个胶囊正好一行放得下。

## 14. WPF 不支持彩色字体 → Emoji 只能单色

**现象**：Emoji 面板和卡片里的 Emoji 都是单色（深色主题下是白色轮廓），而系统里其他程序显示的是彩色 Emoji。

**根因**：WPF 的文本栈不支持 COLR/CPAL 彩色字体；GDI/GDI+ 同样不支持（实测 `DrawTextW` + Segoe UI Emoji
渲染出来仍是单色）。只有 DirectWrite 支持。

**解法**：接受单色，但**必须显式设置前景色**——`Button` 的默认前景色是黑色，在深色主题下 Emoji 会几乎不可见。
卡片文字预览用继承来的前景色即可，Emoji 按钮样式里显式写了 `TextFillColorPrimaryBrush`。

**位置**：`Themes/Styles.xaml`（`EmojiButtonStyle`、`EmojiFont`）

**若要彩色**：见 [08-后续开发路线.md](08-后续开发路线.md) 的方案对比。

## 15. 多显示器 / 高 DPI 下的窗口定位

**做法**：不用 WPF 的 `Left/Top`（DIP 换算在多显示器不同缩放率时容易偏），而是
显示后用 Win32 `GetWindowRect` 取真实物理尺寸，再用 `SetWindowPos` 摆到光标所在显示器工作区的右下角；
同时按该显示器的 DPI 设置 `MaxHeight`，避免窗口高过工作区。

**位置**：`Views/MainWindow.xaml.cs` → `PositionOnCurrentScreen`

## 16. 自动化脚本里的一个坑（工具侧，非程序缺陷）

**现象**：用 `Process.MainWindowHandle` 找不到面板窗口，值为 0。

**根因**：`ShowInTaskbar=False` 的 WPF 窗口会被设置 owner（指向一个隐藏窗口），
而 .NET 的 `MainWindowHandle` 只返回"无 owner 的可见顶层窗口"。

**解法**：工具脚本改用 `EnumWindows` + 标题匹配找窗口（`tools/ui-flow.ps1`、`tools/capture-window.ps1`）。
排查自己的程序时如果发现 `MainWindowHandle == 0`，先想想是不是这个原因。

## 17. Win+V 接管：钩子回调的三条红线 + 抢焦点的两个坑

**位置**：`Services/KeyboardHookService.cs`、`Views/MainWindow.xaml.cs` → `EnsureForeground` / `_showInProgress`、`Services/PasteService.cs` → `ForceForeground`

### 17.1 低级钩子回调的三条红线

1. **不能阻塞**：Windows 对 `WH_KEYBOARD_LL` 回调有 `LowLevelHooksTimeout`（默认 300ms）限制，
   超时未 return 会被系统直接卸载钩子（表现为"用一会儿就失灵"）。
   所以回调里只做：判定 Win 状态 → 注入哑键 → `Dispatcher.BeginInvoke` 异步唤起 → `return 1`。
2. **委托必须强引用**：`_hookProc` 存成字段，否则 GC 回收后原生侧回调 → `CallbackOnCollectedDelegate` 崩溃。
3. **异常不许逃逸**：回调里 `try/catch` 全包，异常穿到原生栈会直接终止进程。

配套细节：`_winVHandled` 抑制长按 V 的自动重复（否则面板疯狂开关）；`_injecting` 防止自己注入的
哑键再次进入判定逻辑。

### 17.2 哑键为什么必须有

返回 1 把 V 键摘掉后，Shell 仍认为"Win 键被单独按了一下"，松开 Win 时会弹开始菜单。
注入一次无功能的 `VK_NONAME (0xFC)` 让 Shell 认定 Win 参与了组合键，从根上避免弹菜单
（AutoHotkey 的 `A_MenuMaskKey` 是同一思路）。

### 17.3 `Activate()` 会被前台锁定驳回

**现象**：Win+V 唤起后，面板浮在最上层，但键盘输入还在原来的窗口里（打不了字）。

**根因**：由低级钩子唤起时，本进程并不是"最后接收输入的进程"，`SetForegroundWindow` 被前台锁定规则驳回；
而 `PasteService.ActivateWindow` 的 `AttachThreadInput` 兜底对自己人无效 —— 目标窗口就是自己的线程，
`targetThread == currentThread` 直接返回 false。

**解法**：`PasteService.ForceForeground` 改为把当前线程挂到**当前前台窗口所在线程**的输入队列上再抢，
最后用 `BringWindowToTop` + `SetWindowPos(HWND_TOPMOST)` 兜底；`MainWindow.EnsureForeground` 以
`GetForegroundWindow()` 的实际值判断（WPF 的 `IsActive` 此时可能是 true），并在延时聚焦回调里复查一次。
管理员权限的前台窗口受 UIPI 限制仍抢不到，只能记警告。

### 17.4 抢焦点会触发"失焦即隐藏"

**现象**：面板弹出来一瞬间就消失（窗口其实还在，只是不可见）。

**根因**：抢前台过程中系统会先送一个 `WM_ACTIVATE(INACTIVE)`，触发 `OnWindowDeactivated` →
`HideOnDeactivate` 直接把刚显示的窗口 `Hide()` 了（此时抢焦点恰好成功，于是出现"隐藏窗口却是前台窗口"的怪状态）。

**解法**：`ShowPanel` 期间置 `_showInProgress = true`，`OnWindowDeactivated` 见到该标记直接返回；
延时聚焦回调（`DispatcherPriority.Input`）里复位。`HidePanel` 也会复位，防止标记泄漏。

### 17.5 真机验收结论（2026-09-19）

Release v1.1.0 在 Win11 23H2（原生剪切板历史开启）上人工核对：按 Win+V → 系统面板不再弹出、
本面板弹出且可直接打字搜索；再按一次收起；Ctrl+Shift+V 与其余主体功能均无回归。
`tools/winv-test.ps1` 只能自动核对"钩子命中 / 面板弹出 / 抢到焦点 / 开关语义"，
原生面板是否被压住必须真机手按（注入输入不触发 Shell 的剪切板历史）。

> **最容易踩的一次**：改完代码后仍启动旧目录的 exe（Debug 编好了却在跑 Release 的旧产物），
> 现象与"功能没生效"完全一样。定位口诀：**先看设置页「关于」的版本号，再看日志里有没有
> `[KeyboardHookService] 已挂载低级键盘钩子`**。

## 已知边界：高权限（以管理员运行）的前台窗口

> 📄 **本节的完整版（定位过程、代码级实测手段、4 个备选方案与代价对比、将来动手的落地要点）
> 已独立成篇：[10-高权限窗口支持决策记录.md](10-高权限窗口支持决策记录.md)。**
> 只想快速了解结论看本节即可；要动这块代码请先读第 10 篇。

**现象**：在**以管理员权限运行**的程序（例如 `run_as_admin=1` 的 Everything）里，按 Win+V 不会唤起本面板，
只会弹出系统原生剪切板；从那类窗口往面板拖文件时面板也会中途隐藏。

**根因**：Windows 的 UIPI（用户界面特权隔离）。实测（独立探针 A/B/C 三组对照，`WH_KEYBOARD_LL` 钩子）：

| 前台窗口 | 钩子是否收到按键 |
| --- | --- |
| 与钩子进程同级（HIGH ↔ HIGH） | ✔ 收到 |
| 高一级（Everything=HIGH，钩子进程=MEDIUM） | ✘ 完全收不到 |
| 高一级窗口最小化后 | ✔ 恢复收到 |

即：**低于前台窗口完整性级别的进程，其低级键盘钩子回调会被系统直接丢弃**，
所以 Win+V 根本到不了本程序，而是原样落给 Shell 的原生剪切板历史。
同理，非提权进程也无法从提权窗口手里抢回前台焦点（`EnsureForeground` 会记
`面板未能取得前台焦点（前台窗口可能以管理员权限运行）`），拖拽因此更难完成。

**当前处置（v1.2.0 决策）**：不修改架构，作为已知边界记录。可选的规避方式：

1. 让那个程序不再以管理员权限运行（Everything：选项里取消"以管理员身份运行"）——零代码改动，最有效；
2. 需要长期支持时，业界标准做法是再引入一个**以管理员权限常驻的轻量钩子进程**（首次启动需一次 UAC），
   由它挂钩并通过 IPC 通知主程序。代价是新增进程/生命周期/IPC 管理，属于架构级改动，
   并会牵出"自动粘贴到管理员窗口"等既有 UIPI 限制。

**顺带实测**：`RegisterHotKey(MOD_WIN, V)` 在本机返回 1409（`ERROR_HOTKEY_ALREADY_REGISTERED`）——
原生剪切板历史占用了这个热键，所以"改用全局热键代替钩子"这条路走不通，
除非关掉原生剪切板历史（`HKCU\Software\Microsoft\Clipboard\EnableClipboardHistory=0` 并重新登录，
本次实测重启 explorer 后该键仍被占用）。
