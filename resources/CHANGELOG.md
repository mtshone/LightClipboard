### 变更 多选图片拖出：有 Ctrl 参与 ⇒ 按点击顺序；纯 Shift ⇒ 仍按列表顺序

**需求原文**（用户提出）：多选图片拖拽输出时，**输出的顺序应该按我点击的顺序**（点选先后），
不要按列表顺序重排。

**新口径（As-is，逐条写死）**：

| 手势 | 输出队列（= 拖出顺序） |
| --- | --- |
| **Ctrl+左键依次点选** | 每点一张**追加到队列末尾** ⇒ 整批按**点击顺序**输出（点 004 → 002 → 001，拖出来就是 004、002、001） |
| **Ctrl 取消后重新点选** | 取消按引用删除；重新点选**追加到队列末尾**（不会回到它原来的位置） |
| **有 Ctrl 参与过，之后又按 Shift** | Shift 只做"**末尾追加扩展**"：区间里**尚未选中**的图片按列表**升序追加到队列末尾**；已在队列里的项**保持原位、不重排、也不被取消**（Shift 不负责排序，也不负责取消 Ctrl 已选项）—— 点击序不被重置 |
| **纯 Shift**（全程没有 Ctrl 参与） | 区间（锚点 → 目标卡片，跳过区间内的文本 / 文件）**整体替换**选择，顺序 = **列表顺序**（由上往下）—— **与 v1.3.0 完全一致**，这一段行为一行未改 |
| 普通单击 / 面板收起 / 列表整体重建（`Reset`） | 清空队列（普通单击同时把该图片设为纯 Shift 的**锚点**；`ClearCore` 一并复位"有 Ctrl 参与"标记） |

队列本身就是"拖出顺序"：`ClipboardSelection._selected` 只做**追加 / 按引用删除**，
`BuildDragItems()` 不再做任何列表序重排（v1.3.0 里那处 `SortByListOrder()` 调用已删除）。

**v1.3.0 交互的其余部分不变**：Ctrl 点**非图片**仍被拒绝（不改动已有选择 + 提示条 `多选仅支持图片`）；
拖动**已选中**的图片 = 拖出整批、拖动**未选中**的图片 = 仍只拖这一张；Ctrl / Shift 按住**不启动拖拽**；
修饰键只在 MouseDown 读一次快照；面板收起 / 列表整体重建清空多选，新内容入库（`Insert` / `Move`）不清空。

### 变更 历史列表支持多选图片：拖动其中任意一张，整批一次性拖出去

**一句话**：在剪切板面板的历史列表里，用 **Ctrl+鼠标左键** 逐张、**Shift+鼠标左键** 选一段
（**只收图片**），然后拖动其中**任意一张已选中的卡片**，把**全部已选图片**以 `FileDrop` 队列的
形式一次性拖到资源管理器 / 聊天软件 / 其它外部程序。

**需求原文**（用户提出）：多选图片，实现"多选图片拖拽输出"。

**为什么这次敢动它**（风险切法）——本版刻意**不碰**任何高危区域：

| 高危区域 | 本版是否触碰 |
| --- | --- |
| `ClipboardWriter` 快照 / 还原（v1.2.4 契约，22 项自检锁死） | **完全不碰**（拖出走 OLE `DataObject`，不经过系统剪切板） |
| `PasteService` 单槽位回调与计时器 | **完全不碰** |
| `StorageService` 批量写库 | **完全不碰** |
| 04 篇不可回退清单（`HideAfterDragOut` / `IsDropInsidePanel`） | **只保住、不修改**：多选**只换 `DoDragDrop` 的入参**，收尾逻辑一个字没动 |
| 多格式数据对象（Bitmap / PNG 单张语义） | **不破坏**：`count == 1` 仍走原来的 `BuildDataObject`，单张路径一行未改 |

**交互规格**：

| 手势 | 行为 |
| --- | --- |
| 左键单击卡片 | **保持现状**：复制 +（按设置）自动粘贴 + 收起面板；**同时清空多选** |
| **Ctrl+左键点图片** | 切换该张的选中状态（已选 → 取消；未选 → 加入） |
| **Ctrl+左键点非图片**（文本 / 文件） | **拒绝**：不改变已有选择 + 提示条 `多选仅支持图片` |
| **Shift+左键** | 从**锚点**到该卡片在列表里的连续区间中，**只把图片加入**选择（区间内的文本 / 文件跳过） |
| Ctrl / Shift 按住拖动 | **不触发拖拽**（修饰键手势的语义是"选择"） |
| 拖动「已选中的图片」 | 导出**全部已选图片**（按 `Items` 的 index 升序） |
| 拖动「未选中的图片」 | 仍只拖这一张（与资源管理器一致） |
| 拖拽被目标接收且松手点在面板外 | 保持现状：`HideAfterDragOut()` 收起面板（受「失焦即隐藏」约束） |

**选择状态规则**：锚点 = 最近一次**普通单击或 Ctrl 点击**的那张图片（连续 Shift 时锚点**不动**）；
选择顺序**始终按列表顺序**（不按点击顺序）—— 保证拖到文件管理器后的排序与面板一致；
> **v1.3.1 修订（历史原文保留，不改写）**：这一条口径已改 —— **有 Ctrl 参与 ⇒ 整批按点击顺序**，
> 只有**纯 Shift**（全程没有 Ctrl 参与）才仍按列表顺序。本节其余提到"顺序 = 列表顺序"的地方
> 同样以 v1.3.1 小节为准（上面的 v1.3.1 小节即为修订后的 As-is 规则）。
**面板收起**（`HidePanel`）与**列表整体重建**（`RebuildView` / `Load` / 切筛选 / 搜索，即
`Items.CollectionChanged` 的 `Reset`）都**清空**选择，而**增量变更**（新内容入库的 `Insert` / `Move`）**不清空**
（选中的图还在，位置变化不影响文件路径）。

`<ExportsDirectory>\<hash[..24]>.png`，**不改文件名**。`ImagePath` 是内容寻址的（`SavePng` 用 SHA-256 前
24 位命名），`StorageService.AddOrTouch` 又按 `Hash` 去重，所以同一次多选里的 N 个图片条目**必然是
N 个不同路径**，不会出现"同一路径重复入队"；源文件缺失的条目**静默跳过**，仍能拖出其余图片。

**本版明确不做**（避免扩大改动面，留待下一期）：

| 项目 | 原因 |
| --- | --- |
| 批量删除 / 批量收藏 | 扩大改动面与回归面，与本次需求无关 |
| 批量粘贴到原窗口 | 会牵动 `PasteService` 单槽位与 `ClipboardWriter` 单份快照的"借一次就还"契约，**风险最高** |
| 批量复制到剪切板 | 剪切板一次只装一种内容，跨类型语义无法自洽 |
| 文本 / 文件的合并输出 | 多选**仅对图片生效** |
| 键盘多选（`Ctrl+A` / `Shift+↑↓`） | 纯鼠标手势的回归面最窄；键盘路径要改 `OnPreviewKeyDown` / `MoveSelection` |
| 批量另存为 / 导出到文件夹 | 独立子需求 |
| 单张图片拖拽行为 | **保持不变**（保住 04 篇不可回退项与现有自检断言） |

**一处与实施方案的偏差（如实记录）**：实施方案 §3.7 要求给 `HistoryList` 加 `SelectionMode="Extended"`，
**本版没有加**，保持 WPF 默认的 `Single`。原因是方案里的理由不成立：`ListBox` 的选中发生在
`MouseLeftButtonDown`（冒泡）阶段，早于我们处理 `PreviewMouseLeftButtonUp`，所以"预览事件已
`e.Handled` 所以不会和 WPF 打架"这个前提是错的。加上 `Extended` 之后：Shift 点击会把区间内的
**文本 / 文件卡片**也画上 1px 强调色"当前项"边框（看起来像被选中，与"多选仅对图片生效"矛盾）；
Ctrl 再点同一张还会清掉 `SelectedItem`（Enter / Delete 失去目标）。多选状态完全由 `ClipboardSelection`
表达，功能验收标准不受影响。详见 04 篇坑点 20.3。

**由此新增的三条坑点**（完整版见 [04 篇 §20](04-实现细节与坑点.md)）：

1. **修饰键只能在 MouseDown 时读一次（快照）**：按住 Ctrl 点下去、**松手前先把 Ctrl 松开**，
   若在 MouseUp 里读 `Keyboard.Modifiers` 就会被误判成"普通单击"——清空多选**并且顺手粘贴一次**。
2. **`PreviewMouseLeftButtonUp` 里不要设 `e.Handled = true`**：隧道事件被吞掉后 `ListBoxItem`
   收不到自己的 `MouseLeftButtonUp`（它在那里 `ReleaseMouseCapture()`），可能留下未释放的鼠标捕获，
   把后续点击一起弄坏。选择手势本身不需要吞事件（`ListBox` 的选中在 MouseDown 阶段已完成）。
3. **"Ctrl / Shift 按下不拖拽"的守卫必须放在位移判定之前**：放在之后会让 `_dragMoved` 先被置真，
   于是"修饰键按住稍微一动"这次选择直接丢失。

### 变更 面板"输出"不再让系统剪切板被"用过一次"的条目占住

**点卡片输出之后，按 Ctrl+V 得到的是剪切板列表**顶部**那条，而不是刚被点出去的那条。**

- **现象**（用户反馈）：历史列表按"最近收录"排，比如顶部是 001、第二条是 002；
  点 002 输出（自动粘贴进目标程序）之后按 Ctrl+V，出来的还是 **002**，
  而面板顶部显示的仍是 001 —— 两个"当前内容"对不上。
- **为什么上一版只修了一半**：v1.2.3 变更（五）删掉的是 `Touch(id)` 与"把自己移到 `_all` 末尾"，
  改的是**列表的排序键**；而"按 Ctrl+V 出来什么"看的是**系统剪切板**，不看面板。
  输出路径必须把内容写进系统剪切板（否则目标程序无从粘贴），写进去之后**没有人把它还回来** ——
  于是"用过一次"的那条依然占着系统剪切板的当前内容，只是不再占着列表首位。
- **落地（"借一次就还"）**：
  - `ClipboardWriter` 增加输出前快照与还原三件套：
    `CaptureForRestore()`（写之前把当前剪切板整份存下来）→ `ScheduleRestoreAfterPaste()`
    （粘贴按键送达后延迟 300ms）→ `RestoreNow()`（把快照写回，含 `HasRestorePending` / `DiscardRestore()`）。
  - `PasteService.PasteIntoWindow(target, afterPasteSent)` 新增"按键**成功发出**后执行一次"的回调；
    只有 `SendInput` 真发出去了才还原 —— 发失败时内容留在剪切板里，用户还能自己 Ctrl+V 补救。
  - `MainViewModel.CopyToClipboard`：只在 `requestPaste = true` 时抓快照；写失败 / 目标窗口无效 /
    只复制路径一律 `DiscardRestore()`（`MainWindow.OnPasteRequested` 里做同样处理）。
  - Emoji 页与点卡片同规则：会粘贴就还，只复制（关掉自动粘贴）就留。
  - 还原写入照样走 `WriteWithRetry`（含 1.5s 屏蔽窗口与 5 次重试）：还原不会触发自己的监听，
    因此列表顺序与排序键依旧不受影响 —— 本版**没有**回退 v1.2.3 的任何一条。
- **还原延迟为什么是 300ms**：目标程序是在自己的消息循环里响应 WM_PASTE 的，
  抢在它读取之前写回，粘贴会拿到旧内容甚至失败。计时器由 `ClipboardWriter` 持有（UI/STA 线程），
  时序为"点击 → 130ms 后发 Ctrl+V → 再 300ms 还原"。
- **快照怎么抓**（先写探针验过再落地，见「验证」）：按 `GetFormats(autoConvert: false)` 逐格式分类：
  - 纯文本（`UnicodeText` / `Text` / `OEMText`）→ 字符串通道（WPF 负责编码）；
  - `FileDrop` → `SetFileDropList`；
  - 位图 → `BitmapSource`（拷成独立像素缓冲，写回用 `SetImage`，由 WPF 生成正确的 DIB / BITMAP 载荷）；
  - 其余（流、`byte[]`、以及 **HTML Format / Rich Text Format 这类"WPF 当字符串读、载荷其实是字节"的格式**）
    → **原始 HGLOBAL 字节**，写回时包成内存流。
    **字符串通道会改写这两类格式**：探针实测 `Rich Text Format` 经字符串往返会被整段吃成空串
    （69 字节 → 1 字节），`HTML Format` 也会被补上尾随 NUL。
  - GDI 句柄类格式（CF_BITMAP / CF_PALETTE / CF_METAFILEPICT）用 `GlobalFlags` 判掉，**不**按 HGLOBAL 强读
    （强读会得到一段垃圾字节）。
- **边界（有意保持不变的）**：
  - **「只复制不粘贴」不还原**（卡片上的 ⧉、右键「复制」、关掉「自动粘贴」后的点卡片）：
    这条路径的语义就是"把这一条留在剪切板里等你 Ctrl+V"。
  - **拖出（拖动输出）本来就不碰剪切板**，无需还原。
  - **还原失败**（剪切板被别的程序长时间占用）时保留输出内容，只记 `[WARN ] 剪切板还原失败`；日志可区分。
  - **输出前剪切板为空、或所有格式都抓不动时不建立快照** → 不还原（不会顺手把剪切板清空）。
  - 还原的是"输出前那份内容"，**不是**"重新写一遍列表首条"：暂停监听期间复制的内容、
    超过 `MaxTextLength` 被截断的长文本，都会原样还回去（这是列表首条之外的第二重保险）。
  - **"暂停监听"期间仍有分歧**：那段时间复制的内容不会被收录，列表首条是停更的，
    而剪切板里是用户刚复制的东西 —— 这是"暂停监听"的本意（不碰用户剪切板），不额外纠正。
  - **收藏项**：收藏会把该条移出「全部」视图，此时"面板顶部那条"取决于用户在哪个视图里看
    （⭐ 视图首条即该收藏项，与剪切板内容一致）；还原永远以"输出前的剪切板"为准。
  - **极慢的目标程序**：若对方在 300ms 之后才去读剪切板（正常程序都在自己的 `WM_PASTE` 里同步读），
    会读到还原后的内容而不是被输出的那条。真要调，改 `ClipboardWriter.RestoreDelayMs` 一处即可
    —— 调大更保险、调小更"跟手"，但**不能调成 0**（那样粘贴会直接拿到旧内容）。
- **由此定下的一条口径**：**系统剪切板内容 ≡ 面板顶部那条**。外部复制会同时刷新两者；
  面板输出只借不占。想"把某一条拿去反复粘贴"，正常路径是 ⧉ 只复制，而不是点卡片。

### 变更（五）面板"输出"不再改变历史排序位置

**点卡片复制 / 粘贴后，卡片留在它在历史里的原位置，不再跳到列表最上面。**

- **起因**：用户反馈"每次输出内容，该内容就被排序置顶到最上面"。排序键被"使用"这个动作刷新，
  列表于是变成"最近用过"而不是"最近收录"：用过一次的老条目突然窜到首位，下次呼出面板时
  位置全变了，想按记忆里的位置找东西就得重新扫一遍。
- **根因**：`MainViewModel.CopyToClipboard` 把内容写回剪切板后调了 `StorageService.Touch(id)`
  （把 `LastUsedAt` 刷成此刻），**并且**把自己移到 `_all` 末尾 + `SortList()`；
  而列表排序键正是 `LastUsedAt` —— "输出"这个动作因此等价于"重新置顶"。
- **落地**（只动输出这一条路径，入库与收藏的语义不变）：
  - `CopyToClipboard` 删掉 `Touch` 与重排，只留"写剪切板 → 通知宿主粘贴"；
    卡片位置、卡片上的时间文案都不再因为输出而变化。
  - `StorageService.Touch(id)` 失去全部调用方，**直接删除** —— 留着就是这条行为的复入口。
  - 排序键的语义收窄为"最近一次**进入**剪切板的时间"：只有 `AddOrTouch`（入库 / 去重命中）
    与 `SetPinned`（收藏 / 取消收藏）会刷新它，两处都补了注释说明为什么这么做。
    **字段名 `LastUsedAt` 保持不变**：LiteDB 按属性名映射，改名会让已落库的旧记录静默丢字段。
  - `MainViewModel.SortList`、`StorageService.GetAll`、`ClipboardItem.LastUsedAt` 的注释一并改写，
    免得下一个人照着"最近使用优先"的旧注释又把 `Touch` 加回来。
- **边界（有意保持不变的）**：
  - **在外部程序里再次复制相同内容仍然置顶** —— 那是剪切板真的又收到了这份内容，属于"新收录"；
    不置顶的话，刚复制的内容会消失在列表深处，反而像"没记上"。
  - **收藏 / 取消收藏仍刷新时间戳**（取消收藏后该条回到历史最上方，方便接着操作）。
  - 拖出（拖动输出）本来就不碰排序键，本次未改动。
- **顺带的语义变化**：`Prune` 也按 `LastUsedAt` 裁剪，于是"列表最下面的先被清理"成了唯一口径 ——
  以前"用过一次"能给老条目续命，现在不会了；显示顺序与裁剪顺序从此完全一致。

### 变更（三）设置页「始终置顶」的说明文字被开关盖住（UI 缺陷修复）

**现象**：设置页「始终置顶」那一行的说明文字钻到右侧开关底下，第一行末尾"…失焦后自动抬"
只剩半个字，看着像被斜着削掉；该项置灰时（上面「失去焦点时自动隐藏」开着）灰色文字叠在
灰色开关上，更像文字直接没了。用户截图（467×696、深色主题）一眼可见。

- **根因**：**排版让位漏写，不是功能坏了**。「标题 + 说明」的 `StackPanel` 与右对齐的
  `ToggleSwitch` 同处一个 `Grid` 单元格，谁也不给谁让位 —— 标题列因此拿到整行宽度
  （@470 窗口宽实测 **402px**），而开关占的是同一片空间的右侧 40px（实测 X=389..429）。
  说明文案有近 70 个字，**按 402px 换行**时最后几个字就排到了开关底下。
  即：开关不是"挤开"文字，是**压在**文字上（坑点 13 窄窗口重叠的同族问题，
  触发条件是"文案够长"而不是"窗口够窄"）。
- **一个必须记下来的排查教训**：这条坑的可见性**取决于折行落在哪**，同一份代码、同一个
  467×696，实测「文字右沿」会在 **−39px（明显压上）** 与 **+1px（刚好擦过）** 之间跳。
  所以"某次量下来没压上"**不能**当作"没问题"的证据 —— 第一版核查脚本就是只按
  "像素有没有压上去"判，在 467×696 上量到 +1px、误判成 PASS，差点把这条改动当成没必要的。
  改判**结构**（标题列有没有给开关留宽度）之后才稳定复现，也才有了下面的反向对照。
- **落地**：`Themes/Styles.xaml` 新增 `SettingRowLabelStyle`（`Margin="0,0,56,0"`，
  56 = 开关实测宽 40 + 16 间隔），设置页里凡有右对齐开关的行，标题列一律套这个样式。
  `56` 不是新数字 —— 「Win+V 拦截」行原先就手写着同一个值（所以那一行一直是对的），
  本次只是把它提成样式，并补上漏写的「始终置顶」行；将来改开关宽度只需改一处。
- **影响面**：纯 XAML 排版，**不动任何设置项、绑定、持久化与窗口逻辑**；
  `KeepOnTopWhenUnfocused` 的行为、默认值与「从属于失焦即隐藏」的关系都没变。
  行高不变（说明仍是 3 行），设置页不会因此需要滚动。
- **顺带核对**：设置页其余 5 行（自动粘贴 / 失焦即隐藏 / Win+V 拦截 / 暂停监听 / 开机启动）
  文案都短，本来就没压到开关，本次未改动。
- **新增回归脚本 `tools/settings-layout-test.ps1`**：把窗口尺寸写进 `settings.json` 再重启，

  现改 —— 那样会踩到 WPF"拖拽式缩放还没重新测量"的状态，页脚会重影到设置页中间，行号对不上）。
  两条判据：**结构**（标题列排版宽度整体避开开关 ≥ 8px）与**像素**（实际画出来的字留 ≥ 8px）。

### 变更（一）拖出（拖动输出）后自动隐藏面板

**把卡片拖到别的程序、并被对方接收后，面板自动收起；取消拖拽或松手仍在面板内时保持显示。**

- **现象**：从面板把卡片拖到资源管理器 / 记事本 / 聊天框并成功放下后，面板一直停在屏幕上，
  与"点一下卡片粘贴完就收起"的观感不一致，只能手动 Esc 或点「隐藏」。
- **根因**：拖拽期间本窗口失焦会被 `OnWindowDeactivated` **有意忽略**（`_isDragging` 分支 ——
  不忽略就会在拖到一半时把面板收掉、拖拽直接断掉），而 OLE 拖拽循环结束后
  **不会再有第二次失焦事件**，于是这次被丢掉的失焦没有任何人来收尾。
- **落地**（都在 `MainWindow` 的拖出分支，不涉及数据、存储与窗口结构）：
  - `OnListPreviewMouseMove` 里 `DoDragDrop` 返回后判断结果：只有目标程序**真的接收**
    （`DragDropEffects != None`）才调新方法 `HideAfterDragOut()`；
    Esc 取消或松在空白处（效果为 `None`）保留面板，免得"拖了一下没成"还要重新呼出。
  - 新增 `IsDropInsidePanel()`：松手位置仍在面板窗口内时**不算**拖出。
    **真机实测才发现**：面板内拖动同样返回 `Copy` —— 面板自己是合法放置目标，
    WPF 会把 `allowedEffects` 原样当作结果返回；只按 `effects != None` 判断，
    "在列表里手抖拖了一下"也会被误当成拖出成功而收起面板。
    判定用 `GetCursorPos` + `GetWindowRect`（都为物理像素，与 `PositionOnCurrentScreen` 同一套坐标口径）。
  - `HideAfterDragOut()` 沿用设置页的「失焦即隐藏」开关：关掉它表示用户要面板常驻，拖出同样不收起。
- **「失焦即隐藏」开关加固（收尾同一问题时的追加改动）**：用户反馈"开关关了还是会收起面板"，
  排查后发现开关本身没问题，但**自动收起不止一条路径**，逐条对齐：
  - `OnDeferredHideTick` 原先**不看开关**就直接 `HidePanel()` —— 计时器可能是开关还开着的时候启动的
    （延迟区间 50–1000ms，用户完全来得及在这期间把开关关掉），到点却照样收起。
    现在计时器到点先复查 `HideOnDeactivate`，任何自动收起都必须服从这个开关。
  - 切换开关时记一行 `[设置] 失焦即隐藏 = 开启/关闭`：以后排查"开关到底有没有生效"，
    日志比界面可靠（界面上的开关只能证明视觉状态）。
  - `MainViewModel.OnPanelShown` 增加 `OnPropertyChanged(nameof(HideOnDeactivate))`：
    每次呼出都按内存里的真实值刷新设置页开关，避免"界面显示关、实际是开"误导排查。
  - 两条失焦隐藏路径也各记一行（`失焦，面板已自动隐藏…` / `延迟隐藏到点，面板已自动隐藏…`）：
    以后"面板怎么自己没了"可以直接在日志里看到是哪条路径、以及当时开关是开还是关。
- 新增三行可检索日志：`拖出成功，面板已自动隐藏` /
  `拖出成功，但「失焦即隐藏」已关闭，面板保持显示` / `拖拽在面板内结束，面板保持显示`。

### 变更（二）常驻面板的「始终置顶」（设置项 `KeepOnTopWhenUnfocused`，默认关闭）

- **起因**：用户把「失焦即隐藏」关掉、想让面板常驻后反馈"点了别的窗口，面板就像自己隐藏了"。
  排查结论：**不是自动隐藏，是被挡住了** —— 面板本身就是 `Topmost`，普通窗口压不住它；
  能压住它的是**同样置顶**的窗口（全屏/最大化浏览器、播放器、其它置顶工具），
  而 Windows 的规则是"置顶层里最后被激活的那个在最上面"，于是点一下那个窗口，面板就落到它下面。
  真机探针证据：点击前面板中心处最上层窗口 = 面板；点击后变成 `Chrome_WidgetWin_1`（`topmost=True`）。
- **落地**：
  - `AppSettings.KeepOnTopWhenUnfocused` + 设置页「始终置顶」开关，
    位置紧跟在「失去焦点时自动隐藏」下面；上面开着时本项**置灰**（面板失焦就收起，谈不上被挡住）。
  - `MainWindow.ReassertTopmostIfPinned()`：面板失焦且本开关开启时，用
    `SetWindowPos(HWND_TOPMOST, SWP_NOMOVE | SWP_NOSIZE | SWP_NOACTIVATE)` 把面板抬回置顶层最上方，
    并再排一次（`DispatcherPriority.Background`）以覆盖对方激活流程更晚才走完的 z 序调整。
    **`SWP_NOACTIVATE` 是关键**：只改层级、绝不抢回焦点，否则用户点别的窗口会被面板弹回来。
  - `ShowPanel` 里也强制抬一次：`Topmost` 本来就是 `true`，再赋一次值不会触发 `SetWindowPos`，
    若此刻正被别的置顶窗口压着，只靠属性赋值抬不回来。
  - 自检加一条 `始终置顶往返一致`（设置持久化），断言数 50 → **51**。
- **顺带加固**：拖拽结束时若 Esc 仍按着（= 这次是"用 Esc 取消的拖拽"），
  400ms 内的那个 Esc 会被吞掉 —— 真机 6 用例回归里出现过一次"取消拖拽后面板被顺手收起"，
  这条只在 Esc 仍按着时生效，不影响平时按 Esc 收起面板。

## v1.2.2 — 呼出面板不再自动聚焦搜索框

### 变更

**呼出面板时光标不再落在搜索框，随手打的字也不会被送进搜索框。**

- **起因**：原先的"呼出即可打字搜索"等于把面板一弹出就置入输入模式 —— 光标在搜索框里闪，
  误触的按键还会悄悄变成过滤条件把列表筛空，看起来像"记录丢了"。
- **落地**（都在 `MainWindow` 的焦点策略里，不涉及数据与存储）：
  - `ShowPanel` 不再调用 `FocusSearchBox()`，改走新的 `FocusPanelWithoutCaret()`：
    清掉子控件逻辑焦点后把键盘焦点交给**窗口本身**（`Keyboard.Focus(this)`），于是搜索框里没有光标。

    残留的过滤条件配上看不见的光标，最容易被当成"记录没了"。

### 已知边界（本次实测确认，未修改架构）

**以管理员权限运行的前台窗口（如 `run_as_admin=1` 的 Everything）无法被本程序接管。**
用独立探针做 A/B/C 三组对照（同一 `WH_KEYBOARD_LL` 钩子）实测：

| 前台窗口 | 钩子是否收到按键 |
| --- | --- |
| 与钩子进程同级 | ✔ 收到 |
| Everything（HIGH，钩子进程 MEDIUM） | ✘ 完全收不到 |
| Everything 最小化后 | ✔ 恢复收到 |

根因是 UIPI：**低于前台窗口完整性级别的进程，其低级键盘钩子回调会被系统直接丢弃**，
Win+V 原样落给 Shell，于是弹出系统原生剪切板历史；拖拽同样因抢不回焦点而中断。
本次评估过的备选方案与结论：

- 改用 `RegisterHotKey(Win+V)`：实测返回 **1409 ERROR_HOTKEY_ALREADY_REGISTERED**（原生剪切板历史占用），
  且临时把 `EnableClipboardHistory` 置 0 并重启 explorer 后仍被占用，此路不通。
- 引入"以管理员权限常驻的轻量钩子进程 + IPC"：业界标准解法，但属架构级改动，本次**未采纳**
  （需求方决定先只做上面两项）。
- 让该程序取消管理员权限运行：零代码改动且立即可用，已写入 README「已知限制」。

完整记录（含实测手段与"方案 B 只能解决拦截、不能解决抢焦点"这一关键提醒）见
[10-高权限窗口支持决策记录.md](10-高权限窗口支持决策记录.md)。

## v1.1.0 — Win+V 接管（低级键盘钩子）

需求来源：[09-Win+V拦截需求与方案.txt](09-Win+V拦截需求与方案.txt)（需求方提供的 Win+V 低级键盘钩子开发方案，原文存档）。

### 新增

1. **`Services/KeyboardHookService.cs`**：`WH_KEYBOARD_LL` 全局钩子拦截 Win+V。
   - 检测「Win 按住 + V 按下」（`GetAsyncKeyState` 判定左右 Win）→ 注入哑键
     `VK_NONAME (0xFC)` 重置 Shell 的 Win 键状态机 → `Dispatcher.BeginInvoke` 异步派发唤起
     → `return (IntPtr)1` 把 V 键从输入流里摘掉（系统剪切板历史与目标窗口都收不到）。
   - 工程约束：委托存字段防 GC 回收崩溃；回调内只做判定与注入，绝不阻塞
     （`LowLevelHooksTimeout` 默认 300ms，超时会被系统强制卸载钩子）；
     长按 V 的自动重复用 `_winVHandled` 抑制；异常一律吞掉，不允许穿到原生栈。
2. **设置项 `EnableWinVHook`（默认 true）**：设置页新增「Win+V 拦截」开关，托盘菜单同步新增同名勾选项；
   开关由 `AppHost` 统一落到钩子的 `Start()` / `Stop()`（订阅 `SettingsService.Changed`），
   关闭后 Win+V 立即交还系统，`Ctrl+Shift+V` 热键始终可用（两条路径并存）。
3. **`PasteService.ForceForeground()`**：强制抢占前台焦点（先 `SetForegroundWindow`，
   失败则把当前线程挂到**当前前台窗口所在线程**的输入队列再抢，最后 `BringWindowToTop` 兜底）。
4. **自检项 47 → 50**：新增「Win+V 低级键盘钩子」分组（挂载 / 运行状态 / 卸载）。
5. **`tools/winv-test.ps1`**：真机端到端验证脚本（`intercept` / `hotkey` 两种模式）。

### 开发过程中修复的问题

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| 面板被 Win+V 唤起后浮在最上层，却打不了字（焦点仍在原窗口） | 本进程不是"最后接收输入的进程"，前台锁定驳回 `Window.Activate()`；`ActivateWindow` 的 `AttachThreadInput` 兜底对**自己的窗口**无效（目标线程 == 当前线程，直接返回 false） | 新增 `PasteService.ForceForeground`：挂到**前台窗口线程**再抢焦点；`MainWindow.EnsureForeground()` 以 `GetForegroundWindow()` 实际值判定，并在聚焦回调里复查一次 |
| 抢焦点过程中面板刚弹出就被自己收起 | 抢前台前的 `WM_ACTIVATE(INACTIVE)` 触发了"失焦即隐藏" | 新增 `_showInProgress` 标记，显示流程内忽略失焦隐藏，延时聚焦回调里解除 |
| 按住 V 时面板反复开关 | 键盘自动重复每次都触发唤起 | `_winVHandled` 标记，V / Win 抬起后才允许下一次拦截 |

### 验收

- `--selftest` 50/50 通过（退出码 0），build 0 警告 0 错误（Debug 与 Release 各构建一次）。
- `tools/winv-test.ps1 -Mode intercept`：面板可见 + 取得前台焦点 + 无其它新增顶层窗口 + 再按一次收起 → PASS。
- `tools/winv-test.ps1 -Mode hotkey`：`Ctrl+Shift+V` 路径回归 → PASS。
- **真机验收（用户实机，2026-09-19，Release 构建 v1.1.0）**：按 Win+V 时系统原生剪切板历史**不再弹出**，
  改为弹出本面板；其余主体功能（监听、粘贴、拖拽、托盘、热键）回归正常。

  重新构建：`dotnet build -c Release`（或 `dotnet publish -c Release` 刷新单文件版）。
