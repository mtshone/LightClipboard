# 08 · 后续开发路线

## 1. 已知限制（当前版本接受）

| # | 限制 | 影响 | 相关坑点 |
| --- | --- | --- | --- |
| 1 | Emoji 显示为单色 | 观感，不影响功能 | [04 第 14 条](04-实现细节与坑点.md) |
| 2 | 无法向管理员权限窗口粘贴 | 少数场景需手动 Ctrl+V | [04 第 12 条](04-实现细节与坑点.md) |
| 3 | 富文本只保留纯文本 | 丢失字体/颜色/超链接 | 设计取舍（架构文档要求存 UnicodeText） |
| 4 | `Ctrl+Shift+V` 会抢占浏览器的"粘贴为纯文本" | 全局热键副作用 | [04 第 11 条](04-实现细节与坑点.md) |
| 5 | **前台是管理员权限程序时，Win+V 完全不被接管**（弹出的是系统原生面板），且拖文件进面板会中断 | 少数场景退化为系统原生行为；需手动点托盘或用 `Ctrl+Shift+V` | [10-高权限窗口支持决策记录.md](10-高权限窗口支持决策记录.md)（v1.2.0 实测确认，**当前决定暂缓**） |
| 6 | 单文件发布常驻内存偏高（≈270MB） | 后台常驻成本 | [04 第 10 条](04-实现细节与坑点.md) |
| 7 | 历史列表一次性载入内存 | 设置页上限 1000 条时启动会变慢 | 见下方改进点 |
| 8 | 无云同步 / 无多设备 | — | 未在需求内 |

> 第 5 条在 v1.1.0 时被记成"面板可能抢不到键盘焦点"，**程度被低估了**。
> v1.2.0 用独立探针实测后修正为：**钩子回调被 UIPI 直接丢弃，Win+V 根本没到本程序手里**。
> 记录见 [10-高权限窗口支持决策记录.md](10-高权限窗口支持决策记录.md)。

## 2. 候选功能（按性价比排序）

### 2.1 彩色 Emoji 渲染（用户已两次提及，值得优先评估）

WPF/GDI/GDI+ 都不支持 COLR/CPAL 彩色字体（已实测：`DrawTextW` + Segoe UI Emoji 仍是单色），
只有 DirectWrite 支持。三条可行路线：

| 方案 | 做法 | 工作量 | 风险 | 结论 |
| --- | --- | --- | --- | --- |
| **A. 自绘位图缓存（推荐）** | 用 DirectWrite + Direct2D 把 Emoji 渲染成位图（`IDWriteTextLayout` + `D2D1_DRAW_TEXT_OPTIONS_ENABLE_COLOR_FONT`），按 (文本, 字号, DPI) 缓存，界面用 `Image` 显示 | 中（约 400–500 行 COM 互操作） | 中：vtable 顺序写错会崩；需大量缓存测试 | 只影响 Emoji 面板与卡片预览，收益直观 |
| B. 引入 Win2D | `Microsoft.Graphics.Win2D` + `CanvasTextLayout`，API 简洁 | 中 | 需把 TFM 改成 `net10.0-windows10.0.19041.0`，发布体积增加约 10MB+ 原生库 | 若后续还要做更多图形效果可考虑 |
| C. 内置彩色 Emoji 图片资源 | 打包 Twemoji/Noto 的 439 个 PNG（约 1.3MB） | 低 | 需网络下载并遵守 CC-BY 4.0 署名；卡片里混排仍需 InlineUIContainer | 最快见效，但引入第三方美术资源与许可义务 |

**建议**：先做一张技术验证页（在 `--demo` 模式下渲染 20 个 Emoji 到 `Image` 上对比效果），
再决定是否全量接入。若采用 A，建议**新增** `Services/EmojiImageRenderer.cs` 承载渲染器，
复用 `ImageCacheManager` 的 LRU 思路做缓存，并在自检里加"彩色 Emoji 渲染非空"断言。

### 2.2 其他功能候选

| 功能 | 落点 | 备注 |
| --- | --- | --- |
| **支持管理员权限窗口的 Win+V（提权钩子伴随进程）** | 新增 `LightClipboard.HookHost.exe` + IPC + 生命周期管理 | 需求真实存在（Everything 即典型）。**动手前务必先读 [10-高权限窗口支持决策记录.md](10-高权限窗口支持决策记录.md)**：里面已写明实测结论、IPC 与生命周期要点，以及**最容易低估的一点 —— 它只能解决"拦截"，不能解决"抢焦点"**（主程序仍受 UIPI 限制），因此可能需要连面板一起放进提权进程，那就退化成"整体提权"（坑点 12） |
| 富文本支持（RTF/HTML） | `ClipboardItem` 加 `RichText`/`Html` 字段 + 解析链 + 卡片标记 | 存储体积会明显上升，建议按需懒加载 |
| 分组/标签 | `ClipboardItem` 加 `Tags`，列表加分组视图 | 需要设计交互 |
| 快捷键完全可配置 | 设置页加热键录制控件 → 写入 `AppSettings` | 建议同时做冲突检测（试着注册一下） |
| Win+V 接管增强 | `KeyboardHookService` + `AppSettings` | 可选：屏蔽键（哑键）可配置、同时接管 Win+Shift+V、拦截计数写入托盘气泡；改前先读坑点 17 |
| 多选批量操作 | `ListBox.SelectionMode=Extended` + 批量删除/导出 | 需要重做拖拽起点判定 |
| 历史搜索高亮 | 卡片模板里用 `TextBlock.Inlines` 分段着色 | 注意 Emoji 代理对 |
| 图片压缩/格式转换 | `ImageCacheManager` 增加 JPEG/WebP 导出 | WebP 需额外编码器 |
| 统计面板（最常复制的应用/类型） | 新页面 + LiteDB 聚合查询 | 低优先级 |
| 便携模式 | 已有 `LIGHTCLIPBOARD_HOME`，只需加"首次运行询问数据目录" | 工作量很小，适合做 |

## 3. 架构层面的改进点

| 问题 | 现状 | 建议 |
| --- | --- | --- |
| `MainViewModel` 偏大（998 行） | 列表、命令、设置、Toast 混在一起 | 拆出 `ClipboardListController`（列表与筛选）、`SettingsViewModel`（设置项）、`ToastService` |
| 历史全量载入 | `StorageService.GetAll()` 一次性读全表 | 改为分页 + 只查列表所需字段（LiteDB 可用 `Select` 投影或分表存长文本） |
| 缩略图在 UI 线程解码 | 转换器里同步解码 | 若历史条目很大可改为异步加载 + 占位图 |
| 服务定位用静态 `AppHost.Current` | 转换器等 XAML 场景需要 | 可接受；若要测试可改为接口 + 注入 |
| 没有单元测试工程 | 只有端到端自检 | 可加 `tests/` 项目覆盖纯逻辑（指纹、文本截断、设置钳制、Emoji 搜索） |
| **UI 状态的"唯一触发源"不统一** | 顶部导航走 `Checked` 事件，其它控件走属性 setter / Command 并存 | 坑点 9 两次踩坑都源于"以为 setter 一定会触发"。建议确立约定：**任何"用户点一下要产生副作用"的地方，副作用挂在事件/Command 上，属性只承载状态**，并写进 [02-源码导读.md](02-源码导读.md) 的代码约定 |

## 4. 技术风险与注意事项

1. **Win32/CopyData 相关改动风险最高**：剪切板与 `SendInput` 出问题时往往只在特定程序上复现，
   改动后务必用真实程序（记事本、浏览器、微信）各验证一次。
2. **单显示器开发容易漏掉多屏问题**：窗口定位、DPI 相关改动请在双屏 + 不同缩放率下验证。
3. **LiteDB 大版本升级**：必须先备份数据库，再跑自检。
4. **不要给控件随意设 `FontFamily`**：ToolTip 会继承（坑点 8）。
5. **不要依赖 `ScrollViewer.Padding` 给滚动条让位**：不同控件模板行为不一致（坑点 7）。
6. **任何"看起来多余"的代码先查** [04 的不可回退清单](04-实现细节与坑点.md#不可回退清单)。
7. **低级键盘钩子（Win+V）改动风险高**：回调里做耗时操作会被系统强制卸载钩子（`LowLevelHooksTimeout` 默认 300ms）；
   且这类改动**必须真机手按验证**，自动化脚本测不出"原生面板有没有被压住"（见 [06 §4.1](06-Win32与系统集成.md)）。
   改完先跑 `tools/winv-test.ps1 -Mode intercept` 回归面板行为，再人工按一次 Win+V。
8. **改了代码要运行对应构建产物**：本项目同时存在 Debug 与 Release 两套输出，曾出现"改完却仍在跑旧 exe"
   导致误判功能没生效（判断依据：设置页「关于」的版本号 / 日志里的功能启动记录）。
9. **跨完整性级别的窗口交互不要靠"猜"**：UIPI 的行为是静默的（钩子被丢弃、抢焦点被驳回都不报错）。
   遇到"只在某个程序里失效"，第一步先查该程序是不是提权的，再按
   [10-高权限窗口支持决策记录.md](10-高权限窗口支持决策记录.md) §7 搭最小探针验证，别直接改代码。

## 5. 需求来源与验收建议

新需求落地时建议沿用本项目的验收方式：

1. 能写进 `--selftest` 的逻辑一律加断言（纯逻辑、存储、格式转换）；
2. 纯 UI 行为用 `tools/ui-flow.ps1` 做"真实输入 + 截图"回归；
   **涉及顶部导航等"按名字而非坐标"的控件，优先用 UI Automation 驱动**（见 [07 篇](07-构建发布与测试.md)）；
3. 涉及系统集成的，必须做一次真实程序端到端验证（复制/粘贴/拖拽各一次）；
4. 系统级快捷键（全局热键 / 低级键盘钩子）除了脚本回归，**还要真机手按一次**，
   并如实记录"哪些结论是脚本验的、哪些是人工验的"（本项目的验收记录写在 [CHANGELOG.md](CHANGELOG.md)）；
5. 完成后同步更新 `resources/` 下对应专题文档与 CHANGELOG；
6. **跨页/跨状态的交互至少要有一条"从非默认状态触发"的用例**（v1.2.0 的"设置页点全部没反应"
   就是只测了默认状态才漏掉的）。
